# 着手评价体系改造 · 设计

## 0. 一句话

「妙手 4 / 失误 50」不是阈值没调好，是**把两个标签放在了同一根单边轴的两端**。
修法有四层，按依赖顺序：换估计量 → 加第二根轴（难度） → 七档 + 发挥水准 → 显示收敛。

## 1. 判据：为什么单靠调阈值救不了

设 `V(P)` 为引擎对局面 P 的评估。`V(P)` 已经**假定后续最优应手**，
所以走出最优手时 `V(P') ≈ V(P)`，走出任何其他手 `V(P') < V(P)`。
于是「这手棋的价值」= `V(P') − V(P)` 这个量：

- **上界卡在 0 附近，下界是长长的负尾。**
- 因此任何建立在这一根轴上的「好/坏」对称标签，**必然一边倒**。

正收益只能来自：搜索噪声、地平线效应、引擎看到这手后修订评估、
低 visits、劫/seki 误判、官子数子误差。实测（§附录 A）表明这些加起来
在 500 visits 下能到 **p95 = 1.34 目、max 1.90 目**。

⇒ 想让「妙手」有意义，**必须换一根轴**。这是本方案的核心，其余都是配套。

外部佐证：Chess.com 的 Brilliant(!!) 也不是「涨了多少分」，
而是「非显然的、带弃子的好手」；星阵的妙手是「AI 第一选点 **并且** 较难被下出」。
两家的顶档都挂在**难度**上，不挂在收益上。

## 2. 第一层：换估计量（低风险，收益立竿见影）

**现在**：`delta_score = scoreLead(N) − scoreLead(N−1)` —— **两次独立搜索之差**，
继承两次搜索之间的全部重评估。

**改成**：同一次搜索内的 `pointsLost = top_moves[0].score_lead − 实战手的 score_lead`
（都取自第 N−1 行的 `moveInfos`，同一次搜索，同一视角）。
实战手不在 top10 时，回退到 `scoreLead(N)` 作为实战手的值。

实测效果（3 盘、500 visits）：**出现「正收益」的比例从 21.7% / 27.4% / 37.2%
降到 0% / 3.7% / 5.8%**。噪声地板大幅下降，1.5 目这样的档位才重新变得可用。

配套：
- 修 `interface.py:1367` 白棋没翻符号。
- 存一列 `points_lost`（新增列，`add_missing_columns` 会自动 ALTER；
  **记得同步 `cron/models.py` 的手抄镜像**，否则会被静默丢掉）。

## 3. 第二层：难度轴 —— 妙手怎么定义

```
妙手  ⇔  实战手 == top_moves[0].move          （走了 AI 第一选点）
        ∧  top_moves[0].prior < P_HARD         （而这个第一选点难以被想到）
```

`prior` 是 KataGo 的 policy 先验，**已经存在 `report_task_moves.top_moves` 里**，
不需要重新分析。

**阈值选 P_HARD = 0.10 的依据**（实测，见附录 A）：

| | 15k 局 | 4k/5k 局 | 李世石 vs AlphaGo |
|---|---|---|---|
| top 手 prior 中位数 | 0.465 | 0.456 | 0.269 |
| P(prior < 0.10) | 8.7% | 8.8% | 20.0% |
| P(prior < 0.05) | 3.3% | 4.4% | 8.3% |

而「低 prior 确实预示人类想不到」也实测成立 ——
P(棋手走出了引擎首选 | 首选 prior 分桶)：

| prior 桶 | <0.10 | 0.10–0.25 | 0.25–0.60 | ≥0.60 |
|---|---|---|---|---|
| 职业局 | 16.7% | 29.0% | 53.1% | 87.9% |
| 4k/5k | 0.0% | 21.4% | 39.0% | 67.6% |
| 15k/15k | 12.5% | 13.0% | 17.9% | 33.3% |

⇒ 职业局：20% 的局面首选 prior < 0.10，其中职业棋手命中 16.7%
⇒ **约 3.3% 的手会被判妙手** ⇒ 288 手的对局约 9 手 ⇒ **每方 4–5 手**。
与星阵截图里观测到的 妙手 1%/3% 同量级。**这个判据自带正确的稀有度，不用再调。**

**必须写进代码注释的两条限制**（不写就会被后人当成万能判据）：

1. **对 15k 这一档几乎没有分辨力**（12.5% → 33.3%，几乎平坦）。
   低段位棋局里「妙手」会退化成「碰巧撞上一个冷门首选」。
2. **官子段 policy 天然更平**（职业局首选 prior 中位数：布局 0.384 → 中盘 0.266 → 官子 0.243，
   官子 p95 从 ~0.90 塌到 0.591）。固定 prior 阈值会**在官子段超额触发**。
   ⇒ P_HARD 要么按阶段给，要么改成「该局面 prior 分布的分位数」。

**玄妙分级**（可选，对齐星阵的 5 级）：按 prior 分桶
`[0.05, 0.03, 0.02, 0.01, 0]` → 1–5 级，柱高即级数。

**更正确但更贵的替代**：KataGo 1.15.0 起有 rank-conditioned human-SL 模型，
每手给 `humanPrior`（指定 `humanSLProfile` 如 `rank_3d`）。
那才是「对这个水平的人来说难不难」的正解，而 `prior` 只是「对 KataGo 来说意外不意外」
（policy 是在剪枝过的 playout 分布上训练的，见 arXiv:1902.10565 §3.2）。
模型文件本机已有（`~/.katrain/b18c384nbt-humanv0.bin.gz`），但要改引擎调用、重跑分析。
**列为后续，不进第一版。**

## 4. 第三层：七档 + 发挥水准

七档（沿用 KaTrain 上游自己的目数梯子 `[0.5, 1.5, 3, 6]`，只是把顶上两档换成新轴）：

| 档 | 判据（`pointsLost`，目） | 说明 |
|---|---|---|
| 妙手 | 最佳 ∩ `prior < 0.10` | 见 §3 |
| 最佳 | 实战手 == `top_moves[0].move` | |
| 很好 | < 0.5 | |
| 可下 | < 1.5 | |
| 欠佳 | < 3 | |
| 失误 | < 6 | |
| 恶手 | ≥ 6 | |

**用目数不用胜率**，依据有三：
- lightvector 的明确建议：让子棋和弱棋手复盘要用 score lead，
  因为让子局里黑方胜率会长期钉在 100% 而目数还在掉。
- 实测胜率会饱和：`|winrate−0.5| ≥ 0.499` 这一桶里，
  平均每手亏 6.6 目只对应 **0.02% 胜率变化**（对比接近均势时 1 目 ≈ 7.9% 胜率，
  分辨率差 2600 倍）。
- 目数噪声可以用引擎自带的 `rootInfo.rawStScoreError` 做逐局面缩放
  （实测 sd(Δscore) 随其四分位 0.136 → 0.672）。**这条列为后续优化。**

**发挥水准**：七档 × 黑白 的直方图。口径照抄星阵实测的（它是对的）：
- 分母 = **该方自己在所选阶段内被评级的手数**，两方各自归一。
- 作用域 全盘 / 布局 / 中盘 / 官子；**没有棋手筛选**（本来就分两色画）。
- 阶段区间用星阵的实测值：**布局 0–59 / 中盘 60–149 / 官子 150–终局**。
  （注意：星阵前端里那个 `[0,60]/[61,180]/[181,e]` 是**死配置**，别抄。）

它的价值在于：**把「50 处失误」这个诚实的事实以分布形式说出来，
而不是铺成一面 50 行的墙。**

## 5. 第四层：显示收敛

- 妙手 / 失误 两个列表**每方各取前 N（N=5）**，按 `pointsLost` 降序（妙手按 prior 升序）。
- 加**阶段**筛选（全盘/布局/中盘/官子）与**棋手**筛选（双方/黑/白）。
  换阶段时**每个窗口重新分配一份 N 的预算** —— 这正是星阵「可以查看出更多」的机制。
- Tab 标题上的数字要**诚实**：显示 `妙手 (4)` 但实际有 20 个时，
  写成 `失误 (5 / 50)` 或在列表底部给一行「另有 45 处，按阶段查看」。
  **不能像星阵那样只显示截断后的数** —— 那会让用户误以为只有 5 处。

外部佐证：OGS 也是这么做的 —— `getWorstMoves` 取 100 个、
按 delta 排序、门槛 −5.0 目，**每方截到 3 个**，界面显示 6 个；
而且**门槛不够时回退到直接取前 N**，保证干净的棋局里也有「关键手」可看。
星阵是每方 5 个（选单方时该方 10 个，但屏幕总数恒 ≤10）。

## 6. 可选第五层：阈值随水平缩放

AI Sensei 的做法（从它的 bundle 里读出来的）：
门槛表 `blunder 2.5 / mistake 1.0 / inaccuracy 0.3` 是**归一化值**，
实际门槛 = 该值 × `nwa(段位)`，`nwa` 在 `{30k: 15, 8d: 1.8, 9p: 1}` 上分段线性插值。
默认取对局双方段位的平均，缺省落在 1k（scale 4.65）。
⇒ **1k 的「失误」是 4.65 目，9p 的「失误」是 1.0 目。**

这直接对上你说的「分析业余选手的棋局时失误明显多于妙手」。
建议做成一个「评判尺度」选择器（默认取对局双方段位，可手动覆盖），
**第二期做**，因为它需要先确认 `user_games` 里有没有可靠的段位字段。

理论依据：Regan & Haworth (AAAI 2011) 证明原始平均损失**不是尺度无关的**，
需要 `dμ = 1/(1+x) dx` 的对数缩放，且缩放后的统计量对 Elo 单调
（2700 分 0.056 → 1600 分 0.133）。

# 实施记录（2026-08-29，分支 feature/move-grading）

## 落地的东西

**唯一真源：`katrain/core/move_grade.yaml`。**
七档、目数梯子、妙手判据、显示上限、阶段区间全在这一份里。
`katrain/core/move_grade.py` 读它、判级、并生成前端常量
（`python -m katrain.core.move_grade --emit-ts` →
`katrain/web/ui/src/features/analysis/gradeTiers.generated.ts`）。

两个部署边界必须显式处理，不然只会在容器里炸：

* `Dockerfile.cron` **只 `COPY katrain/cron/`**，且此前 `katrain/cron` 对外零跨包
  import。现在显式加了一行 COPY 带上 `move_grade.py` / `move_grade.yaml` /
  `sgf_parser.py`，并由 `tests/test_move_grade.py::test_cron_container_copies_the_grading_module` 守着。
* **PyYAML 与 chardet 原本不在任何 requirements 里**，两个容器各自装各自的，
  所以三处（`requirements-cron.txt` / `requirements-web.txt` / `pyproject.toml`）都补了。

## 第一层：换估计量 ✅

`points_lost = 对落子方最优候选的 score_lead − 实战手的 score_lead`，
两个数取自**同一次搜索**（第 N−1 行的 `moveInfos`）。实战手不在候选里时
回退到下一行的根评估，并把来源记在 `points_lost_source`
（`in_search` / `two_search` / `none`）—— 口径不同的行必须能被分辨出来。

一个坑：不能直接取 `top_moves[0]`。`order` 是按 `playSelectionValue` 排的，
实测 17.7%~34.4% 的局面里 order-0 不是 scoreLead 最优的候选，直接用会算出负损失。
代码取的是候选里对落子方最优的那个。

## 第二层：难度轴 ✅

`妙手 = 走出引擎首选 ∩ 首选 prior < 0.10 ∩ 局面尚未决定`。
第三个条件借自 Chess.com Brilliant 的成文判据「即使你没找到这手，也不能是已经完全赢定的」，
实现为 `|scoreLead| <= 20` 且胜率落在 [0.05, 0.95]。
玄妙指数 1–5 按 prior 分档；官子段按 `phase_prior_scale` 收紧阈值
（职业局首选 prior 中位数 布局 0.384 → 官子 0.243，不收紧会在官子超额触发）。

**visits 闸量的是 `root_visits`，不是 `visits`。** 后者存的是首选的 childVisits
（`report_analyze.py` 取 `move_infos[:1]` 的 visits），拿它当「搜够了没有」的闸
会静默压制妙手。为此新增了 `root_visits` 列。

## 第三层：七档 + 发挥水准 ✅

档位用 KaTrain 上游自己的目数梯子 `[0.5, 1.5, 3, 6]`。
`TrendChart.tsx` 新增第四个 tab「发挥水准」：七档 × 黑白的分布，
**分母是该方自己在所选阶段内被评级的手数**，两方各自归一；
未评级的手不进分母但单独报出来，免得分母悄悄变小把发挥吹高。

## 第四层：显示收敛 ✅

每方各取前 5（`selectPerSide`），加阶段（全盘/布局/中盘/官子）与棋手（双方/黑/白）筛选。
**换阶段时每个窗口重新分配一份预算** —— 这正是星阵「可以查看出更多」的机制。

与星阵不同的一点是**计数诚实**：tab 上写 `失误 (5 / 50)`，列表底部还有一行
「另有 45 处未列出」。星阵只显示截断后的数，会让人以为整盘只有 5 处问题。

## 顺带修掉的 bug

1. `katrain/config.json` 的 `eval_thresholds` 方向反了（升序，而 `evaluation_class`
   要降序）⇒ 六级梯子塌成两级，亏 ≥0.5 目全落最差档。已恢复
   `[12, 6, 3, 1.5, 0.5, 0]`，并把 `TeachingSettingsDialog.tsx` 里按位置配对的
   档位标签一起翻正（那份升序清单大概就是当初翻错方向的诱因）。
2. 报告管线的 SGF 解析换成 `katrain/core/sgf_parser.SGF`：让子石不再被丢、
   起手方不再写死黑、分支不再拍平进主线、老式 `;B[tt]` 不再变成盘外坐标 `U0`。
   畸形 SGF 现在会抛，调用方捕获后把任务标 failed 并写明原因。
3. `interface.py` 的 `delta_score` 补上白棋符号翻转。
4. **测试静默改写被提交的 `katrain/config.json`**（见 `current-state.md` §5.3）。
   这条是修第 1 条时被它咬出来的 —— 修好的值被吃掉过两次。
   `tests/conftest.py` 加了按用例恢复的夹具。**这大概也是那份升序值的由来。**
5. 五份阈值合一：报告链路（服务端判级）、`live/models.py`、`cron/analysis_repo.py`
   （它原本用 -1.0，与其余三处的 -1.5 不一致）、两个研究面板双胞胎，
   现在全部取自 yaml。

## 旧报告怎么办

改造前生成的报告 `grade` 列为 NULL。这些行里 `top_moves` / `actual_move` 都还在，
所以 `GET /reports/{id}/moves` 会**按需补算**（`_moves_with_grades`），不用重新分析棋局，
也不用让前端再实现一份判据。补算只读，不写回库。

## 没做的（明确留下）

* **段位缩放**（第五层）：AI Sensei 的做法是门槛 × 段位系数（1k 的失误=4.65 目、
  9p=1.0 目）。要先确认 `user_games` 里有没有可靠的段位字段。
* **`ai.py:232` 的 `max(0, points_lost)`**：没有动。它是 accuracy 计算的一部分，
  在本次范围内没有消费者，改它等于动 accuracy 语义，风险大于收益。
* **研究面板换难度轴**：两个双胞胎现在只统一了阈值来源，判据仍建在相邻局面
  score 之差（两次搜索）上，噪声大。要换轴得先让它们拿得到 `top_moves[].prior`。
* **棋盘每手评级色带**：`kiosk-shell/tokens.css:859-901` 那条现成的 `.kiosk-ribbon`
  还是零消费者；`Board.tsx` 的 6 档 `EVAL_COLORS` 也没扩成 7 档。
