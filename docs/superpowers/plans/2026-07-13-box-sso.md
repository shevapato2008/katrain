**Date:** 2026-07-13
**Status:** Design locked, not started

**Confirmed decisions (user, 2026-07-13):**

## 1. Why

用户痛点:每次退出围棋再进入,又要重新登录。真因**不是** token 丢失或过期 —— token 存在 katrain 前端的 `localStorage`(key `token`,7 天有效)一直都在。真因有两层:

1. **前端启动竞态 bug**(katrain):`AuthContext.tsx:102` 用 `isAuthenticated = !!user`,而 `user` 要等异步 `GET /me` 返回才有值;`KioskAuthGuard.tsx` 在 `/me` 未回来时就同步判"未登录"跳 `/kiosk/login`。而"退出围棋→再进"本质是 launcher `:8080` → katrain `:8081` 的**整页浏览器跳转**(`launcher.js` 用 `window.location.href`),每次重挂 SPA → 每次命中竞态,人卡在登录页。
2. **各 App 身份彼此隔离**:`localStorage` 按 origin(含端口)隔离,`:8081` 存的 token 对 `:8082`(象棋)等其它 App 不可见。所以即便修好竞态,也只是"围棋单 App 不再重复登录",达不到用户要的"一次登录用所有功能"。

目标:开机在 launcher 登录一次 → 全盒所有 App 都认得你,退出/切换 App 不再重复登录。

## 2. Current state (grounded)

**katrain(身份能力齐全,是天然身份中心):**
- 用户库:SQLite `users`(`katrain/web/core/models_db.py`),字段 `id, uuid, username, hashed_password, rank, credits, is_admin, avatar_url, created_at`。
- 鉴权:`katrain/web/core/auth.py` — bcrypt(passlib)+ JWT(python-jose,HS256,`SECRET_KEY`)。`create_access_token`(type access)、`create_refresh_token`(type refresh)。
- 端点:`katrain/web/api/v1/endpoints/auth.py` — `POST /login`、`POST /refresh`、`POST /register`、`GET /me`、`POST /logout`。
- Token 生命周期:`config.py:40-41` `ACCESS_TOKEN_EXPIRE_MINUTES = 60*24*7`(7 天),`REFRESH_TOKEN_EXPIRE_DAYS = 90`。前端**从不调用 `/refresh`**。
- **"信任外部身份→签发本地 token"现成模式**(board-mode):`auth.py` `login()` 的 `remote_client` 分支 + `_get_or_create_shadow_user`(username → 本地占位用户 `SHADOW_USER_NO_LOCAL_AUTH`,再签发本地 JWT)。这是"信任盒级身份"的模板。
- Token 传输:`OAuth2PasswordBearer`(`auth.py:18`)只读 `Authorization: Bearer`。**全仓库无任何 `Cookie(...)` 读取**。唯一 token-in-URL 先例:WebSocket `/ws/lobby` 用 `?token=`(`server.py:1577-1592`)。
- 前端:`kiosk/pages/LoginPage.tsx` → `useAuth().login()`;`context/AuthContext.tsx`(kiosk + galaxy 共用)`login()` → `POST /api/v1/auth/login` → `GET /me` → `localStorage.setItem('token', ...)`;挂载时 `useState(() => localStorage.getItem('token'))` + `useEffect` `fetchUserProfile`。守卫:`kiosk/components/guards/KioskAuthGuard.tsx`(同款 galaxy `AuthGuard.tsx`)。`LoginPage` 无"已登录→跳回"逻辑。

**smartbox-software(无任何盒级身份):**
- setup-wizard `/launcher`(`templates/launcher.html` + `static/js/launcher.js`):单活 App 切换器 — 点卡片 `POST /api/launcher/switch`(`services/launcher.py` 起停 systemd unit)→ 轮询 `/api/launcher/status` → `goTo(url)`(`launcher.js:33` `window.location.href`)。**无 auth/login/user/session 概念**。
- App URL(`config.py`):`LAUNCHER_GO_URL = http://127.0.0.1:{KATRAIN_PORT}/kiosk`、chess/xiangqi/gomoku/hermes 各自 `http://127.0.0.1:<port>/`。**无反代,全是裸 loopback 端口。**
- mini-apps(chess / xiangqi / gomoku):**无任何用户/账号/session**(其 `db.py` 只有 `games` 表,无 user 列)。它们今天不 gate 谁在用。
- `routers/platforms.py`(微信 QR 等):是**单 App 外部账号绑定**(hermes ↔ 微信),**不是**盒级身份。

**关键平台事实:** cookie 按 **host(域)**共享、不按端口 —— `127.0.0.1` 的 cookie 会发给 `:8080/:8081/:8082/...` 所有 App;`localStorage` 按 origin(含端口)隔离。这使"共享 cookie"成为唯一**零反代、零改各 App 前端**就能打通全盒的传输。

## 3. Desired end state

1. 开机(或 launcher 首次加载)若无有效登录 → 显示**盒级登录页**(launcher 上,复用围棋登录页视觉),支持**登录 / 注册 / 切换用户**。
2. 登录成功 → 浏览器持有一个 **`127.0.0.1` 域、跨端口共享的 cookie**(内含 katrain 签发的 JWT)。
3. 进入围棋/象棋/国象/五子棋/hermes,**都无需再次登录**;退出某 App 回 launcher、再进另一 App,也不再问。
4. katrain 完全按 cookie 里的身份工作(复盘 / 棋力 / 学习记录归到该用户);mini-apps 暂不需要改(不 gate),身份可用作**后续**给它们加 per-user 记录的基础。
5. "切换用户 / 登出":launcher 清 cookie(+调 katrain `/logout`),回登录页。

## 4. Architecture

```
浏览器(单 chromium 实例)
  │  1. 在 launcher(:8080)提交 用户名/密码
  ▼
setup-wizard(:8080)  ── 瘦身份客户端(新 routers/auth.py)
  │  2. 服务端 loopback 调 katrain POST /api/v1/auth/login(或 /register)
  ▼
katrain(:8081)  ── 身份中心(复用 bcrypt/JWT/users)
  │  3. 返回 JWT
  ▼
setup-wizard 在**自己的响应**上 Set-Cookie: sb_token=<JWT>; Domain=127.0.0.1; Path=/; HttpOnly; SameSite=Lax; Max-Age=7d
  │  4. 浏览器存下 127.0.0.1 域 cookie(跨端口)
  ▼
之后访问任意 App(:8081/:8082/...):浏览器自动带上 sb_token
  katrain 后端:get_current_user 在 Bearer 之外**加 Cookie 兜底** → 认得
  mini-apps:今天不 gate,无需改;将来读同一 cookie 即可归属 user
```

**为什么 setup-wizard 端设 cookie(而非 katrain 端):** launcher 页在 `:8080`,若让 katrain(`:8081`)在跨源 fetch 响应里给 `127.0.0.1` 设 cookie,涉及跨源 Set-Cookie / SameSite 麻烦。让 setup-wizard 服务端 loopback 调 katrain 拿 token、再在**同源(:8080)响应**上设 `Domain=127.0.0.1` cookie,浏览器按 host 存储 → 自动发给所有端口,规避跨源问题。这正是 katrain board-mode `remote_client` 模式的**反转**(这次 setup-wizard 当 client,katrain 当 authority)。

**Cookie 安全:** `HttpOnly`(JS 读不到,防 XSS 偷 token)。katrain SPA **不需要**读它 —— 挂载时直接 `GET /me`,cookie 自动带上,成功即已登录。`SameSite=Lax` 足够(全是同 host 导航)。仅本机 loopback,`Secure` 可不设(http)。

## 6. Risks / open questions
- **CSRF / SameSite(Phase 2 硬性要求)**:cookie 兜底让所有 `get_current_user*` 端点都接受环境 cookie。Phase 2 设 cookie **必须 `SameSite=Lax`**(跨站不带),并对**无 body 的状态变更端点**(如 `/logout`,无 JSON body → 无 preflight)评估 CSRF token / Origin 校验。GET `/me` 本身安全。
- **WebSocket 需 Origin 白名单**:Phase 3 给 WS 加 cookie 认证时**必须同时加 Origin/Host 白名单**(WS 握手不走 CORS,否则 CSWSH)。Phase 1 已据此保持 WS `?token=` only。
- **HttpOnly cookie vs katrain 现有 localStorage Bearer 并存**:galaxy / 完整 web 版仍用 localStorage header 路径 —— cookie 兜底是**新增**、不移除 header,两者共存不冲突(header 优先)。确认 galaxy 版不被 cookie 逻辑干扰。
- **SameSite / 跨端口 fetch**:launcher 若用**服务端**代理(推荐)则无跨源;若某处改用浏览器直连 katrain,需复核 CORS + SameSite。坚持服务端代理设 cookie。
- **Token 生命周期**:7 天 access;kiosk 常开,靠 refresh 静默续期或直接延长 access。Phase 1 先接 refresh 或延长。
- **多用户 UX**:共享 kiosk 上切换用户的物理流程(谁在用)——本次做"显式切换用户"即可,不做人脸/自动识别。
- **登出安全**:HttpOnly 只有服务端能清 → 登出必须走 `POST /api/auth/logout`(Phase 2),前端清不了。
