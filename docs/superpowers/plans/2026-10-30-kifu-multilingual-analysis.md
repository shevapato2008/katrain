# Kifu Multilingual Analyzer Decision and Implementation Addendum

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

> **当前状态：调研完成，用户已明确恢复开发、部署与测试。** 最终执行决策已并入主计划第0.1节；选择方案B，姓名exact保留，cn/tw赛事IK、jp Kuromoji、ko Nori、en standard，组合词同赛事AND/五语字段OR。以下“候选/待确认/暂停”表述保留调研过程记录，不再阻止已授权实施；实际安装和token效果仍须TEST先验，新配置不冒用原两轮评审的结论。

**Goal:** 按姓名、姓名片段、赛事完整名称和赛事组合词的不同检索目标，确定五语分析方案及验证方法，避免错误切词、误召回和索引重复膨胀。

**Architecture:** 保留现有精确keyword与字面子串路径；如用户确认需要赛事多关键词检索，只给赛事的五语字段增加各语言合适的text子字段，不把人名精确匹配改成分词检索。五语显示与同一棋手/赛事身份沿现有数据库绑定，分词器不负责翻译、身份归并或语言间名称映射。

**Tech Stack:** Elasticsearch候选9.5.5及匹配插件；keyword / wildcard / text multi-fields；候选IK、ICU/CJK、Kuromoji、Nori、standard/english分析器；未来受控`_analyze`和真实小语料搜索验证，当前不运行。

## 1. 对当前计划的判断

主计划为`2026-10-30-kifu-elasticsearch-search.md`。它明确采用keyword完整名称及wildcard字面子串，**没有IK，也没有按语言配置自然语言分析器**。

| 目标 | 当前方案是否覆盖 | 是否需要语言分词 |
|---|---|---|
| 搜“王星昊”，准确找到他的棋谱 | 已设计，实施未完成 | 不需要，完整名称keyword最直接 |
| 搜英文、日文、韩文等完整姓名 | 已设计五语词条与身份关联 | 不需要每个名字拆词；不能让姓名分词后误中其他棋手 |
| 搜“王星”等连续姓名片段 | 已设计literal子串兼容 | 使用既定wildcard路径，不依赖词典是否认识该姓名 |
| 搜完整赛事名或连续赛事片段 | 已设计keyword/子串 | 不必分词 |
| 搜“国手 山脉 半决赛”等非连续组合词 | 尚未设计 | 需要先确认组合词语义，再选择赛事text分析器 |

因此，原计划对原有“精确＋连续子串”目标合理；**不能将它宣称为已覆盖新增的多关键词中文/多语自然语言检索**。需要补充的是检索语义、字段分析、插件兼容、实际效果与容量验收，不是机械安装五种“排名最好”的分词器。

研究阶段曾将两条路线一并呈现。用户随后明确“开始实施”“开发、部署、测试都完成以后通知我”，并要求将最终决策并入主计划。现按保留精确+增加赛事多词的方案B执行；采用本补充方案建议的同赛事AND/五语OR，不增加完整自然句理解。正式验收是实际PROD 100QPS完整HTTP每请求≤200ms。

## 2. 五语候选与建议

五种名称语言是简体中文cn、繁体中文tw、日语jp、韩语ko、英语en。其余现有UI语言仍按主计划使用英文metadata，不能将11个API语言值缩成5个。

| 字段语言 | 完整姓名/完整赛事 | 如需赛事多关键词，优先评估 | 需要核对的限制 |
|---|---|---|---|
| 简体中文 | keyword；姓名片段保留wildcard | IK的ik_max_word/ik_smart组合，与ICU、内置CJK基线比较 | IK不是ES内置插件；围棋专名、届数、比赛阶段的切词须看实际token，不靠通用口碑判胜 |
| 繁体中文 | keyword，保留原字形 | ICU/CJK与IK繁体语料比较后选择 | 不能把面向简体的SmartCN直接当繁体最佳；不能假设IK默认词典对繁体专名完整 |
| 日语 | keyword | 官方Kuromoji；ICU/CJK作为对照 | 棋戦名、人名、数字与番勝負切词可能不同；人名仍有exact保护 |
| 韩语 | keyword | 官方Nori；ICU/CJK作为对照 | Nori明确提供韩语词典、复合词处理及用户名词词典；不能把ICU通用分段当作同等韩语形态分析 |
| 英语 | keyword | standard为短赛事名的起点，english作对照 | english包含词干/停用词处理，可能改变专名和缩写；不因为英文就一律用stemming |

**候选建议不是效果已验证的最终选择。** 原则是每个赛事字段最终只保留一个选中text分析方案；不是把IK、ICU、CJK及所有模式都长期复制成索引字段。

ICU适合作为多语统一比较基线；它的Unicode规范化/词典分段能力不等于自动翻译，也不能据此说对所有语言都最好。简繁中文是字形/词汇差异，已有cn/tw字段均可检索；无需为完整姓名跨简繁查找强制改写原数据。拼音、错字纠正及新同义词产品不属于本次必做范围。

### 版本兼容的当前证据

- ES官方候选镜像9.5.5-amd64存在，发布目录记录2026-09-30。当前并未下载该镜像。
- 官方ICU、SmartCN、Kuromoji、Nori文档有对应9.5.5插件包。

## 3. 最小字段设计与查询规则

### 方案A：保留原功能，少依赖

- 玩家：已有`player_terms`完整keyword＋既定literal子串。
- 赛事：已有`event_terms`完整keyword＋既定literal子串。
- 五语归属与显示沿同一实体ID和现有已确认词条，不对所有姓名使用standard中文拆字。
- 不装分词插件。该方案满足原契约，不新增多词组合能力。

### 方案B：精确路径不变，增加赛事多词分析

1. 姓名exact、public player_id、授权范围和原优先级保持主计划规则；完整名字命中时不把赛事分词混入，避免错误扩大棋谱集合。
2. 赛事完整名称仍走keyword；原literal子串保留。新增text只用于用户确认的赛事组合词场景，不能以新total覆盖旧case来掩盖回归。
3. 五语赛事分别用各自分析器；检索覆盖合适的五语字段，**不能仅按UI语言限制输入语言**。英文界面输入“王星昊”仍能精确找到同一棋手。
4. 组合词默认AND作为待确认基线，避免任一常见词就命中大量无关比赛；停用词过滤后无token时返回无匹配，不能变成全库匹配。
5. 默认仍按原日期/id稳定排序，不擅自切成BM25相关性排序。若用户需要相关性排名，应另行明确，不混入本次性能承诺。
6. 分词器只决定文本如何切分、归一；“吴清源”和“Go Seigen”的同一身份关系来自已有名字数据/显式映射，不由IK/Kuromoji自动推断。

### 避免多存一份五语赛事正文

采用ES multi-fields：五语原赛事值在_source只保留一次，对该值建立精确keyword与选中的text子字段。现有主计划的`display`是enabled:false对象，若为其中赛事建text子字段，必须将该层改成显式dynamic:strict映射，按需开启event字段；不能在enabled:false父对象下假设子字段会被索引。

仅示意结构，分析器名称由样本选择后确定；当前不执行：

```json
{
  "display": {
    "type": "object",
    "dynamic": "strict",
    "properties": {
      "cn": {
        "properties": {
          "event": {
            "type": "keyword",
            "fields": {
              "words": {
                "type": "text",
                "analyzer": "kifu_cn_index",
                "search_analyzer": "kifu_cn_query"
              }
            }
          }
        }
      }
    }
  }
}
```

实际映射还需明确其它四语、姓名显示字段与来源对象；未参与搜索的显示/来源仍不额外建索引。通用`event_terms`可继续作为跨语精确匹配入口，不需要把整份metadata按语言复制五份。

## 4. 获准恢复后的可执行步骤

本文是计划，下面步骤须在用户确认目标并明确恢复实施后执行。

- [ ] **A1：固定检索语义。** 确认选A还是B；B需确认AND组合词、原日期排序及精确姓名优先。将变化只加入generic赛事分支，不放宽原public/scope边界；记录新的预期集合与旧oracle不变部分。
- [ ] **A2：固定插件候选。** 查匹配ES9.5.5的官方/维护者包、校验和与descriptor；不使用latest或不明镜像。按候选组合建一个受控测试环境，不按五语各建一个集群。
- [ ] **A3：建小语料样本。** 使用下表真实五语短语，另加少量明确标注的组合词、误召回与完整人名反例；不先重建17.7万盘索引。测试环境和样本有明确清理路径，不留五份候选索引。
- [ ] **A4：比较_analyze。** 逐语言比较候选的index/query tokens、位置和停用词影响，记录实际token而非预想切词。示例未来请求为`POST <test-index>/_analyze`，body包含已配置field及样本文本。不能只因token看着合理就判检索有效。
- [ ] **A5：比较检索集合。** 姓名exact零误召回、原字面片段不退化；赛事组合词有人工可解释的预期命中/不命中。检查语言输入与UI语言不一致、简繁、数字届数、日文番勝負、韩文复合词及英文缩写。小样本统计precision/recall与误召回原因，不承诺某个分词器绝对最佳。
- [ ] **A6：只保留必要词典。** 若确有围棋术语误切，只添加最小版本化用户词典；完整姓名本已有keyword保护，不把所有姓名都强制加入分词词典。词典修改不自动改写旧token；选择和版本必须在首次全量导入前固定，不建设远程热词服务。
- [ ] **A7：重测容量。** 加text后统计每种字段与选中插件的索引、段合并、CPU/RSS。原0.3–1.5GiB album估计不是分词后的保证；主计划2GiB整体store停止阈值及8–10GiB峰值预算不自动增加。若超限报告取舍，不能为启用更多分词偷偷扩盘。
- [ ] **A8：修订主计划和schema。** 更新Task2 mapping、Task3固定镜像/插件、Task4 generic查询与Task6语义case；明确哪部分保留原两轮评审结论、哪部分是新增方案。未通过的新语义不能冒称已获Astra批准。
- [ ] **A9：恢复开发和最终验收。** 用户明确继续后再处理8个暂停草稿，不从旧worker上下文自动续跑；先小样本确定，再一次性建立最终全量索引。最终仍按主计划完整HTTP100QPS、真实网页、增量同步、旧方案清理和四步发布流程。
