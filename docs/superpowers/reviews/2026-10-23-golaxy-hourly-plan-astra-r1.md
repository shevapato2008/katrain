## 通过依据

- 小时流程先扫描有页数、条数、HTTP 次数和时间上限的头部，再处理窗口内候选：默认 5 页、最多 10 页；默认 160 次 HTTP、最多 240 次；SGF 尝试最多 100 次。取消 rolling 深扫；2021 年旧待办在下载前即排除。源未提供可信更新时间时，只报告本轮指纹差异，不声称能确定源在过去一小时更新。
- 新候选优先，已见条目采用持久的最久未检查顺序；不在头部的近期已见条目复核仍占用同一 100 次 SGF 总预算。触顶明确报告覆盖不足；手动扩大范围仍受相同硬上限约束。
- 计划已区分“StateStore 见过”与“已有 catalog/native receipt”。未发布且因 token、凭据或临时错误延期的条目，指纹不变时继续原待办；已发布不变条目才跳过准备与翻译。同 ID 变化保留原件和差异证据，不覆盖冻结包或产生重复源行。
- 7004 仅在 SGF/shared 查询中终止；其他单条失败采用有限重试、冷却和隔离，429 保持整源退避。七条旧记录的迁移有精确证据条件、默认 dry-run、原像及摘要、离线/兼容锁要求和摘要核对回滚，不删除失败证据或伪造成功。
- 78 盘恢复以既有原生发布回执为边界，历史尾段只做相应验证，不启动历史翻译或发布。完整 album 验证检查点绑定 manifest、receipt、目标、算法及语言；五语、SGF、姓名、来源和中文公开卡片全部通过后才记进度，最终完整覆盖后才能推进状态。
- HTTP 使用绝对剩余时间的外层 `wait_for`，不再把 httpx 读等待超时当成整个请求的墙钟上限。错误记录区分网络 `ReadTimeout` 与阶段超时，避免误导后续恢复。
- 本次只做本地修复、聚焦测试和审核；未授权的生产写入、推送、合并、部署、真实模型/导入、RK 与 Smartbox 操作均排除。未来部署步骤明确属于另行授权后的说明。

## 实现时保留的最小核对点

以下是计划既有要求的具体落点，不要求另建测试或审核框架：

1. “完整扫描有限重叠范围”必须包括遇到窗口外旧条目后继续扫描；用旧条目夹在新条目前面的假分页验证，不能假设列表按比赛时间或创建时间排序。跨两轮预算测试同时覆盖复核公平性与未发布待办续跑。
2. 检查点只复用已完成 album 的全部检查；保存新进度不能无限刷新旧证据的 24 小时有效期。失败、部分完成、绑定变化和过期均不能贡献最终成功覆盖。
3. 当前新包仍走原完整 TEST → 五语验证 → PROD → 验证流程；“历史只验证”的限制不能误套在新包上，也不能因同 ID 更新隔离而篡改原发布状态。

## 已明确接受的范围限制

3300 秒是现有协作预算，**不是整个进程的严格墙钟上限**。现有同步 DB、发布线程及全量 SGF 缓存预热可能超出它；不能用外层取消假装这些工作已停止，也不能在先前写线程尚可能运行时另启发布。此次承诺的真实网络截止是 600 秒 source 阶段与 300 秒旧包 API 验证尾段。该限制已在计划中公开，并获任务负责人按比例保留；本审核不要求为本次源扫描修复重构整个发布引擎。

默认窗口和页数不代表近期全集完整。计划采用的五页样本（100 个唯一 ID，69 个位于七天窗口内）为默认值提供有限依据；源分页实测及日期列表诊断应保留在指定证据文档中，不应把局部采样包装成全量覆盖或已解决的生产性能结论。

本结论是计划批准，不是实现、测试通过或生产恢复证明。后续按计划完成聚焦验证和最终 diff 审核即可，无须追加第二轮计划审核。
