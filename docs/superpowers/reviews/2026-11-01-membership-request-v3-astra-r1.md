# Membership request v3 — Astra Max review, round 1

**Verdict: Needs revision. Critical: 0. Important: 2. Minor: 2.**

本轮独立审核对象为 [v3 修订设计](../specs/2026-11-01-membership-points-and-request-budget-v3.md) 的 155 行版本；这是新 v3 设计的第 1 轮，不是旧 v2 计划或 Fixture 的第三轮。本轮只读设计、证据、相关旧边界与少量源码，做本地纯数值复算并写入本报告；未运行 benchmark、访问数据库／生产／GPU／凭据，未修改产品或主设计。用户允许本修订最多两轮。

## Important

### I1 — 报告“等值盘数”没有同时应用自然周上限，造成高级权益承诺错误

**位置：** v3 §5.2 第 78 行；相关 §7 第 111–114 行、§8 第 127 行、§9 第 147–150 行。

现稿写“若全用高级，Plus 期内能完整做 7 盘”，但一份 300 手高级报告需要 `4 × 301 = 1204` 单位，周上限为 2107，且整份只能选择一个来源全额预留。因此每自然周最多一份；30 天只跨 5 或 6 个自然周，新开通、无已有周耗用时，实际最多 5 或 6 份，不能完成 7 份。`9030 / 1204 = 7.5` 是忽略周节奏的总预算等值，不是可交付份数。剩余周单位可以用于普通报告或短分析，但不能拼成同周第二份完整高级报告。

同样，续费不重置本周已用时，“30 盘普通”也应明确是预算等值，而非任何生效排期都能用满的保证。例如旧 term 在周一已用完 2107，新 term 周二开始，接下来的 30 天只剩四个可用自然周窗口，最多完成 28 份 300 手普通报告。

**最小修订：** 保留用户确认的 9030／2107，不加额度、不拆份跨周预留、不新增拼单。把第 78 行改成总预算等值与周上限共同限制的说明，给出高级 5／6 周和上述续费算例；购买／续费前明确显示本周已用会延续，所有盘数均为参考。验收增加“一周第二份高级被拒、30 天实际窗口约束、续费首周已满”的聚焦断言。Root 已接受该修正方向，尚待写入正式设计后复核。

### I2 — 删除报告资源桶后，Free 的按份数资格与到期衔接尚未形成完整契约

**位置：** v3 §7 第 112–116 行；§8 第 130 行；§9 第 139、150 行。

“每周一份报告”与统一标准单位不是同一计量维度。50 手报告和 300 手报告都占一份 Free 资格，却分别需要 51／301 个标准单位；相同单位数也可能全部来自短分析。现稿明确升会员时携带真实单位，却没有明确会员到期转 Free 后，本周已有会员报告、仅短分析、wallet 报告、尚在运行的报告分别怎样影响体验资格。若只按第 139 行保留统一 week 单位桶，执行者可能将 Free 错设成 301 单位、漏掉预留，或在到期时额外发一份体验。

**最小修订：** 明确保留服务端报告份数资格事实，可复用现有 Free 计数或 operation 账本，不增加通用资源钱包。冻结以下语义及两个代表性边界验收：

- 有效会员期内不额外领取 Free；本周 `free_report`／`membership` 来源报告已成功或仍预留／运行时占用体验资格。
- 失败退款释放原授权周资格；原周归属不随完成时间移动，删除终态内容仍保留 receipt。
- 仅做过短分析不算已领报告；到期后若本周未用／未预留报告，且 P3 合格，可领原本未用的一份 Free。wallet 报告不占赠额；默认先用可用 Free，有意选钱包须明确确认。
- Free 转付费后继续携带本周真实标准单位，新 term 总量不扣过去的 Free；同一事务维护资格与单位预留，不能双领或半扣。

以上与 root 在本轮提出的最小规则一致，能够闭合缺口；需要写入 v3 的账务及计划修订段，不能只留在讨论消息里。无需新平台或额外研究。

## 已核实且无需扩张的部分

- **N+1 与费用：** 300 手为 301 标准单位，Plus 周 2107／期 9030；2000 visits 为 1204 单位。钱包标准 2 credits、高级 8 credits，完整报告 602／2408 credits，即 6.02／24.08 积分，算术正确。
- **实测来源：** JSON 共 75 行，状态 complete；归档脚本 SHA-256 与 JSON 记录一致。tf3 串行 `8 / 18.726770449 = 0.427195924`，三并发 `23 / 31.002688444 = 0.741871146`，模型 SHA 与记录一致。两个端口不合并为两卡吞吐，b28 未被偷换成报告模型。
- **成本复算：** 按 2,592,000 秒／30 天、4200 元情景及 κ=0.5，tf3 单位成本为 0.007586076／0.004368334 元，Plus 满用为 68.5023／39.4461 元。89／249／799 的折扣、毛利、月容量和收支平衡人数与 v3 JSON 对得上。29 元无法覆盖两种指定情景的结论正确。
- **敏感性：** κ 是假设而非本次 GPU 利用率；若串行情景 κ 降到 0.3，Plus 满额分摊成本约 114.17 元，89 元对应约 -28.3% 分摊毛利；κ=0.7 时约 48.93 元。现稿已说明需求不足、固定支出和业务额外成本，候选“保守价”不能变成无条件盈利承诺。未来销售容量闸门应继续按现稿保留，无需本轮追加压测。
- **领地：** 500 领地与同深度支招共享搜索结果，不产生额外的四分之三节省；不同位置小样本也不能证明 ownership 开关的因果差值。[KataGo 官方协议](https://github.com/lightvector/KataGo/blob/master/docs/Analysis_Engine.md) 支持同次结果包含候选与可选 ownership，并说明 ownership 会带来额外开销。现稿未把 visits 当成实际 NN 推理次数。
- **钱与权益：** 1 积分固定显示为 100 旧整数 credits；新充值、存量余额、旧 SKU 含赠额、合法旧订单、旧在途授权按原整数与版本保留。会员标准单位是到期权益，不是可购第二钱包；用户未批准的价格与补贴没有被偷定为正式目录。
- **原安全边界：** v3 §6、§7、§9 明确保留真实模型／深度／完整 0..N 交付、失败全退与退款后重授权、迟到 worker fencing、删除／旧 requeue／reaper、原分析入口与 state/WS 出口守卫、固定事务锁序、幂等履约、Kiosk 不可变云端身份、mock 的实际 TEST 数据库隔离、P3 身份前置和真实支付／容量／发布闸门。此次只检查这些边界没有随商品简化被删掉，不重新开展旧计划第三轮评审。
- **双端与状态：** 用量／会员／积分充值三页签、两项统一上限、会员卡不展示内部等值积分、固定 viewport 的后续视觉确认方向清楚。旧 Fixture 尚不是 v3，产品尚未实现／部署／收款的状态表述诚实。

修正 I1、I2 后可请求本修订的第 2 轮复核；M1、M2 可一并做小幅证据说明。仍然不构成用户批准候选价、允许亏损促销、代码验收或生产发布。
