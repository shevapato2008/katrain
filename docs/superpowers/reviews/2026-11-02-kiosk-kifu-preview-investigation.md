# Kiosk 棋谱预览与 Galaxy 回放差异调查

## 结论与此前判断的更正

这三份 SGF 可以解析，但包含占用交叉点的 B/W 着法。它们不满足普通围棋对局的落子规则，**不能因此判定为不合法 SGF，更不能据此删除棋谱**。

[SGF FF4 的围棋执行规范](https://www.red-bean.com/sgf/go.html)要求将所记棋色放到目的点，覆盖该点此前的内容，再进行提子及自提处理。[B/W 属性规范](https://www.red-bean.com/sgf/properties.html)也要求查看器执行语法正确的着法，即使它违反围棋对局规则。规范允许记录异常着法、变化和编辑位置；记录浏览与对局裁判有不同职责。

此前调查把 `Space occupied` 直接称为“坏谱”，以及把 Galaxy 覆盖落点描述成错误容忍，都过于武断，此处更正。Galaxy 在占用点覆盖这一点符合 SGF 查看语义，但不能由此宣称其完整实现了 FF4 的全部语义。

Kiosk 的列表预览与棋谱详情均调用 `/api/v1/baipu/load`，后者通过 `BaseGame._validate_move_and_update_chains` 进行对局规则校验。Galaxy 在前端用 `sgfToMoves` 与 `buildReplayBoardState` 回放，允许覆盖占用点。因此同一份原始 SGF 的详情 HTTP 200，到了 Kiosk 的严格解析却返回 HTTP 422，并被统一显示为预览加载失败。设备上的核心解析文件哈希与本地一致，两个 1989 年对照棋谱实际返回 200；证据不支持网络或 RK3562 性能导致这三个错误。

## 全库只读检查

两库分别使用只读、可重复读事务导出。每库 176,949 条物理记录、176,690 条可见记录；各有 176,940 个不同 SGF 哈希。两库 SGF 内容哈希集合相同，但近期 ID 不完全一致，因此将内容检查结果按哈希分别映射回各库的记录及隐藏/重复标记，没有直接沿用另一库的 ID 或比例。

| 范围 | 总量 | 严格回放拒绝数 | 比例 |
| --- | ---: | ---: | ---: |
| 正式库可见记录 | 176,690 | 718 | 0.406361% |
| 测试库可见记录 | 176,690 | 718 | 0.406361% |

全部 718 条拒绝记录均来自 `19x19` 源目录：686 条在主线报 `Space occupied`，24 条报 `Single stone suicide`，4 条报 `Suicide`，4 条在初始位置构造阶段报 `Unexpected illegal move (Space occupied)`。这是**现有严格解析器的拒绝率，不是不合法 SGF 的占比**。扫描覆盖每份记录的第一主线；不宣称对所有变化分支及全部元数据做了完整 FF4 合规审计。

临时安装于诊断目录的独立 sgfmill 1.1.1 对全部 176,949 条记录做了语法解析、主线着法坐标和摆子点集检查，另发现 16 条需要复核的格式/坐标问题，全部为可见记录，其中 9 条也落在上述 718 条严格拒绝记录内：

- 5 条包含超出 19 路范围的 `ot` 着法：正式库 5543、6025、8691、39308、49301。
- 1 条着法值为 `pd;W`：正式库 28896。
- 6 条含以数字开头的属性名 `7LKO`，违反 SGF 属性名语法：正式库 26580、26581、26582、26583、26584、26608。独立库的报错文本是 `unexpected end of SGF data`，并非这些文件的结尾确实缺失；已核对具体异常属性。
- 4 条根节点的 AB/AW 在相同点同时指定不同颜色：正式库 32937、32938、32939、32940。

此外存在 115,470 条多 GN 值的历史元数据兼容警告；未把这种元数据问题混入主线回放故障率，也没有将未被上述检查发现的问题视为“完全合规”。独立 astra/max 对属性和值进行实际分词后，确认当前全库没有 AE、压缩摆子范围或落子后的 AB/AW；本次显示对齐不会顺带重写这些一般性支持边界。

## 修复范围

独立 astra/max 第一轮计划审核通过。实现将 Galaxy 现有的纯回放算法提取为共享工具，Kiosk 列表预览和详情逐手查看共同使用，避免把屏幕查看交给实体摆谱规则校验。原始谱仍从真实 API 读取。

已用新共享解析/回放函数离线复核全部 718 条严格拒绝记录，718 条均产生可用盘面且无黑白同点输出。这只证明当前显示算法能够解释这些记录，并不等同于 718 条全部经过浏览器逐盘验收，也不把原始记录的格式问题自动修正。

本次不改变实体盘摆谱的 backend-authoritative 步骤、摄像头或灯控协议。**上述三个案例在实体盘摆谱会话中仍会遇到原有严格 422**；屏幕回放对齐不等于实体引导已支持覆盖点操作。本次不修改或删除任何数据库记录。

## “最近摆过”的独立发现

该 Tab 未接账号个人摆谱历史 API。SGF 缓存、最近记录和进度只写入按用户 UUID 隔离的浏览器 localStorage；游客写入内存。实际 RK3562 Chromium 以 `--incognito` 启动，当前进程于 2026-11-02 22:16:35 开始，浏览器重启会清空这类存储。实查当前浏览器没有 baipu 历史/SGF/进度缓存；不能据此断言该账号从未摆谱，也无法从该 Tab 自动恢复其他设备或较早浏览器会话的记录。

进入实体盘摆谱时才写最近列表；仅查看棋谱不写。另有代码级问题：KifuPage 在挂载时读取一次 recent，不会在账号身份解析完成后重新读取，此窗口可能显示空列表；本次未把这个潜在竞态冒充为当前缓存缺失的已复现原因。修复账号历史持久化不属于本次 SGF 显示对齐。
