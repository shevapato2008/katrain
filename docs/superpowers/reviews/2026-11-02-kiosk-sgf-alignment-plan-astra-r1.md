# Kiosk / Galaxy SGF replay alignment — independent plan review, round 1

**Status: APPROVED.** No material issue requires a second plan-review round. This approves the planned screen preview/replay change; implementation and final code review are still pending.

Reviewed `docs/superpowers/plans/2026-11-02-kiosk-galaxy-sgf-replay-alignment.md`, repository `AGENTS.md`, the supplied user-level constraints, the actual Galaxy/Kiosk consumers, SGF parser, replay helpers, physical-board entry point, relevant tests, and local investigation evidence. No product files, database records, device state, or commits were changed by this review.

## Findings

No blocking findings.

- **Root cause and SGF distinction are supported.** Kiosk preview calls `BaipuAPI.load` at `KifuPage.tsx:125–129`; detail does the same at `KifuDetailPage.tsx:59–70`. `katrain/core/baipu.py:83–88` applies the playing-rule validator to both placements and moves. Galaxy imports the common `utils/sgfSerializer` at `KifuLibraryPage.tsx:37`, then parses the original SGF at lines 277–285. Its board function overwrites the point at `LiveBoard.tsx:196`. The three stored response/collision examples support this explanation. Occupied-point rejection alone does not establish invalid SGF: the [SGF Go execution procedure](https://www.red-bean.com/sgf/go.html) allows overwriting and defines capture/self-capture; [the property definitions](https://www.red-bean.com/sgf/properties.html) distinguish move execution from setup. These sources do not establish that Galaxy implements all SGF semantics, and the plan correctly avoids that claim.
- **The shared-code boundary is sound.** Plan lines 48–74 extract the actual six pure functions, preserve `LiveBoard` exports for existing consumers, and derive SVG coordinates from one matrix implementation. Those functions have no component dependency. `LiveBoard` only needs `parseMove` and `buildReplayBoardState` after extraction; `ReplayBoard3D` can retain its existing imports. The plan's TypeScript and Kiosk 2D build checks cover the relevant integration boundary without requiring unrelated backend regression.
- **The physical-board boundary is justified for this reported screen failure.** `PhysicalBoardButton.tsx:26–30` passes the original SGF into the separate session. Changing that session would require reviewing its authoritative steps, captures, camera and LED behavior. The proposed screen fix neither requires nor justifies that expansion. The original SGF cache/navigation contract can remain intact.
- **The implementation split is practical.** Tasks A and B own separate files and share a frozen function interface. The controller owns the read-only audit. Fixture SGFs remain in test-only locations; the runtime uses real API data. The plan covers both preview and detail, setup offsets, explicit colors, passes, coordinate orientation, cancellation/stale data, transport errors, and representative real-record/device checks.
- **Known unsupported SGF constructs are not an observed current-corpus regression.** I independently tokenized property/value pairs across all 176,949 production export rows, excluding property-looking text inside bracketed values. This found zero AE properties, zero compressed AB/AW/AE ranges, and zero AB/AW properties after a B/W property. The three target files also match the reported move/setup counts. This is a targeted inventory, not proof of general parser or SGF conformance; preserving Galaxy's existing limitations remains a reasonable scope decision for this fix.

## Nonblocking implementation and reporting clarifications

1. **Make “usable SGF” executable and test it.** Plan lines 34, 86 and 88 already require this. `sgfToMoves` does not throw when the input lacks a game tree: `sgfSerializer.ts:289–296` returns no nodes, and the caller receives empty arrays. A nonempty-string check plus `try/catch` alone therefore cannot meet the requirement. Reject missing/whitespace/junk content or a parse with no usable replay entries; keep a deliberate policy for valid setup-only or zero-move records. A focused component regression is sufficient. Do not turn this patch into a new general SGF validator.
2. **Keep the remaining physical limitation explicit in the final result.** Plan lines 7, 89 and 110 should be understood to mean that the three records become viewable on screen while their physical-board sessions still encounter the existing `/baipu/load` rejection. Merely saying “the protocol is unchanged” would obscure that user-visible limit. No additional physical-session implementation is needed for approval.
3. **Attribute audit outcomes per environment and per row.** Plan lines 26 and 97 should be updated with the controller's completed snapshot evidence. Equal SGF hash sets allow reuse of content-level audit results even when album IDs differ. They do not by themselves establish equal per-row rejection counts or visible-library rates. Join results back by hash to each environment's own rows and visibility flags, retain its IDs/source paths, and report syntax/property findings separately from strict playing-rule rejection. The controller has confirmed it is taking this approach.
4. **Use one focused stale-board regression while updating the existing detail tests.** The current `KifuDetailPage.tsx:86` gates metadata by language but not album ID, while its board is derived independently at lines 113–115. Plan line 88 explicitly fixes that exposure. Verify that an old board and its actions disappear while a different ID/language request is pending or fails; the existing slow-language-response test alone only checks the hero text.

No tests were rerun for this plan-only review; the controller's reported baseline is not represented here as an independent execution result. The next appropriate step is the authorized parallel implementation, followed by the planned focused verification and independent code review.
