## 必须修正

### P1 — 原生增量发布的精确来源/公开记录契约尚未纳入同局去重，生产应用顺序也未保护仍运行的旧实现

计划第 37 行要求保留原生 manifest v1/v2 和精确重试；第 45、69、74 行只分配了 `scripts/import_kifu.py` 与 `catalog_backfill.py` 的指针适配。实际星阵增量入口 `katrain/kifu_ingest/catalog.py` 还有独立的约束：

- 首次发布已有来源时，约第 1950–1967 行将同一 `origin_path` 的全部 `KifuAlbumSource` 所属行与精确 SGF 命中集合比较。把旧谱来源以 `reviewed_same_game` 聚合到不同字节的主记录后，来源拥有者集合包含主记录，而主记录不属于精确 SGF 集合，于是触发 `existing source path content changed`。
- 约第 1873 行的已有 manifest 重试，以及约第 1996 行的已存在来源/精确内容复用，均调用 `_require_public()`；该函数约第 371 行明确拒绝 `duplicate_of_id` 非空的原记录。即使保留了全部原始 SGF、来源和旧 receipt，隐藏其记录也会破坏这些路径。`kifu_ingest/sync.py` 还按原始 receipt 验证公开卡片，不能仅让发布器略过 public 检查。
- 这不是只涉及 CWI 的假设边界：本轮从冻结的 `dedupe-census-groups.json` 和 `dedupe-census-rows.jsonl.gz` 重算，186 组双方身份已解析且元数据相容的候选中，**98 组为 19x19 ↔ 19x19**。例如 `907/6086`、`1579/8236`。主记录优先星阵仍会隐藏另一条星阵来源记录。

此外，Controller 第 81–83 行计划直接应用双库修复，同时明确不部署应用代码。候选代码的隔离运行验证不能证明当前运行中的发布器、重试验证器或人工导入入口能安全消费新指针。原有 v2 快照在旧 API 中安全降级，不能推导出新的同局指针也具备同样兼容性。

**所需最小计划修正：**

1. 为上述原生发布/重试/公开验证路径明确分配窄范围责任和验收；采用精确原始来源与已审 journal 区分“源记录”与“展示主记录”，继续把原始 receipt、rank snapshot 和分析绑定原 SGF。不得把不同 SGF 的主记录冒充原始发布内容，也不能全局放宽 `_require_public` 或来源内容校验。
2. 至少覆盖一组 19x19 ↔ 19x19 的审定同局指针：原始来源精确重导入、存在的原生 receipt 重试、公开主记录验证；伪造或已漂移 journal 仍拒绝。如果当前范围选择暂不支持某一原生契约，必须将相应依赖明确列入 dry-run 排除条件并报告，不能宣称精确重试已兼容。
3. 双库 apply 前检查实际运行版本、写入者和相关原生 receipt/待验证依赖，确保拟应用组与仍运行代码兼容。可以缩小当前可应用 cohort；若必须先安装兼容代码，则不能在“不部署代码”的步骤下先激活不兼容指针。本审核不要求新增未经授权的发布，也不要求审完全部 1,885 组。
