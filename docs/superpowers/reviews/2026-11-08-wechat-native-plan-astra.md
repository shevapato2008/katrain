## 阻塞项

### B1：把公钥模式和错误响应的实际协议写入客户端契约

位置：计划产品契约 3–4、Task 2（原行 23–24、51–54），上线配置步骤（原行 98–99）。

当前只写配置微信支付公钥并对响应验签，没有明确请求的 `Wechatpay-Serial`。商户处于迁移状态时，省略该头会选用平台证书签名；仅配置公钥 ID 的实现随后会拒绝真实成功响应。另一方面，“响应均验签”和“重放拒绝”未区分无签名错误响应与可安全重复处理的有效通知。

最小修改：

- 每个请求发送 `Wechatpay-Serial: <配置的 PUB_KEY_ID>`；上线前确认商户通知签名已采用所支持的公钥模式。未知 ID 继续拒绝，不为本次扩建证书自动下载系统。
- 2xx 响应（含 204 空正文）必须验签后使用；非 2xx 只形成有界、稳定的传输/渠道错误，有签名时验证，但不得把无签名 `ORDER_NOT_EXIST`、关单错误或错误文案当作不存在、已关闭或付款成功的权威事实。
- 响应和通知均以 HTTP 签名时间戳检查约 ±5 分钟的新鲜度。旧签名拒绝；窗口内合法重复通知仍经过幂等到账并成功应答，不能用一次性 nonce 消耗规则误拒正常重复。

最低验收：请求头断言；204 空文体验签；过期/未来签名拒绝；无签名非 2xx 不改变订单终态；有效重复通知仅到账一次。

依据：[公钥迁移规则](https://pay.weixin.qq.com/doc/v3/merchant/4012154180)、[验签及时间戳](https://pay.weixin.qq.com/doc/v3/merchant/4013053420)、[Native 关闭订单](https://pay.weixin.qq.com/doc/v3/merchant/4012791881)。详细字段已在 `output/wechat-native/official-contract.md` 留档。

### B2：明确冻结请求和“取消/到期与尚未完成的创建”竞态

位置：产品契约 2、5–9、Task 3（原行 22、25–29、62–67）。

计划正确要求同商户单号恢复和网络在事务外，但“支付元数据”过于笼统：只冻结商户/AppID 仍可能在重试时改变描述、通知地址或有效期。仅有本地 15 分钟也不能保证微信订单采用该截止时间。更关键的是，提交本地 pending 后、Native 创建网络调用完成前，取消或到期检查可能先查询到 `ORDER_NOT_EXIST`；若据此终结，而原创建稍后成功，就会留下本地已取消但微信仍可付款的二维码。

最小修改：

- 首次创建前持久化完整业务请求参数：商户、AppID、商户单号、描述、金额/CNY、通知地址、明确的 `time_expire=expires_at`。重试读取冻结参数；签名时间戳/nonce 可更新。运行配置改变不得改写旧单绑定或延长有效期。
- 明确创建阶段与取消意图的最小持久状态。尚未取消且未到期时允许同单号、同参数重试；取消意图或到期后禁止再启动新的 Native create。已发出的创建可能晚完成，须保留确认中并查单/关单收敛，只有已验证的付款/关闭事实（或可证明从未发出的本地单）才可终结。查询 404 不能证明并发创建最终不存在。
- 迟到 create 响应不得重新露出取消/到期二维码；迟到已付款事实仍走统一原子到账。旧参数因剩余有效期不足而不可再创建时，继续确认/关闭原单，不刷新 `time_expire` 以“修复”请求。

最低验收：冻结后修改配置仍使用原请求；断网重试商户单号和业务正文不变；本地截止传入微信；用可控传输 barrier 覆盖“创建已发送→取消查询404→创建晚成功→继续关单/支付到账”，证明不会假终结或恢复二维码。

依据：[Native 创建字段及有效期](https://pay.weixin.qq.com/doc/v3/merchant/4012791877)、[Native 状态流程](https://pay.weixin.qq.com/doc/v3/merchant/4012791891)。竞态处理是应用侧推论，不是微信提供的额外事务保证。

## 已有实现带来的定向提醒（不扩大方案）

- `payments.order_receipt()` 当前会单凭本地时间把 pending 投影成 expired；`reconcile_order_in_transaction()` 也会本地终结。新 wechat 路径必须落实计划中“已确认才终结”的约束，保留 mock 原有测试语义即可。
- 现有后台 `order_by(id).limit(100)` 对长期未知订单会反复命中同一批。实现现有“节流 + 单笔隔离”要求时，同时采用简单到期重试时间/游标或公平分页，避免第 101 单永远得不到漏通知补偿；不需要新增队列基础设施。
- 回调提交后才应答是正确选择。按官方 5 秒应答预算限制 DB 锁等待；拿不到锁就回可重试非 2xx。无须为本次另外建设异步消息系统。
- 设备新增 cancel 继续使用现有 `_identity_bound_request`；读、写、取消和迟到响应都受同一云身份快照约束。手机跨屏提示应在下单前可见，避免用户付款页才发现无法用本机扫码。

第二轮已完成并批准。实现后以计划中的聚焦协议、账务并发、设备身份与 11 语检查为准；不要求扩展退款、全量回归或重复设计审核。本审核没有执行产品测试，也不把计划批准当作支付实现验收。
