## 必须修订

### R1-01 · P1 · A1/A2/A3：把用户确认的局面绑定到服务端输入

计划第 35 行固定发送 `input:{session_id}`，第 53 行仅用前端 snapshot 丢弃旧响应。这不能证明服务端报价对应用户眼前的局面。

现有 `_position_input` 会在请求到达时读取服务端当前 SGF（`katrain/web/api/v1/endpoints/paid_analysis.py:40`）；仅当请求同时携带 `sgf` 时才会核对其局面指纹。`usePaidPosition` 的 `snapshotKey` 只存在于本地 scope，未发送给服务端（`katrain/web/ui/src/features/analysis/usePaidPosition.ts:35`、`:70`、`:99`）。

可发生的顺序：浏览器仍显示局面 A → AI 已走到 B、WS 更新尚未到达 → 报价请求携带 session_id 抵达 → 服务端对 B 报价 → 用户仍在 A 上确认 → B 的报价与执行一致，正常扣费，结果却可能投影到仍未更新的 A。现有签名报价防住的是“报价后局面改变”，没有防住“报价前服务端已改变而 UI 未知”。自由对弈比静态研究页更容易遇到此情形。

最小修订要求：

- 明确选定一个客户端预期局面契约，quote 与 execute 都携带；可复用已有 `session_id + sgf` 校验，但必须确保 SGF 确实来自用户所见的完整当前路径、规则、贴目和摆子，不能从现有 stones 猜历史。若用窄的预期快照标识，须把其生成、请求字段和校验文件列入 A1/A2，而不是建立通用快照系统。
- 预期局面校验、play/normal 限制和 SGF 捕获应针对同一个 session 锁内快照。失配返回明确 `position_changed` 类错误，在预扣和引擎请求前终止。
- 当前局面失配应清除原确认并等待下一次主动点击。现有 hook 对所有 409 自动重新 quote（`:124–126`），不能让这一分支悄悄改成另一局面的报价。
- 增加一个“服务端已换手但浏览器仍显示旧状态”的聚焦用例，再覆盖报价之后换手的拒绝；断言无扣费、无引擎调用、无错误局面投影。无需添加广泛并发测试矩阵。

已确认执行后发生换手，仍按既有 operation 结算并丢弃不再匹配的投影即可；本问题不要求另造取消、退款或冻结 AI 落子的商业规则。

### R1-02 · P1 · B1/B3：手机号登录若保留，必须归一到云端正式账号身份

计划第 73 行新增“登录允许私有手机号查找”，第 92 行只写 shadow/SSO 边界保持，没有指定这个新增身份别名跨板端的落点。

当前非 strict 板端登录先将输入转发云端，随后直接用 `login_data.username` 建本地 shadow（`katrain/web/api/v1/endpoints/auth.py:436`、`:459`），并以其生成本地 token。云端一旦允许输入手机号登录，原样复用这条路径会把完整手机号变成板端公开 username；同一云账号用用户名和手机号登录还会产生两个本地 shadow，违反本计划的隐私与同账号边界。

最小修订二选一，并在第二轮前选定：

- 若手机号登录并非当前用户验收要求，删除这一额外扩展；本次只要求新注册完成手机号验证，继续以公开用户名/密码登录。
- 若保留手机号登录，明确云端解析后的正式账号标识是唯一权威；板端取得已验证的云 `/me` 身份后，才用正式公开 username 建/复用 shadow、绑定 remote client 和签发本地 token。手机号只作为私有登录凭据，不能传入公开 username、JWT subject 或 Box bootstrap 的账号名。也须明确旧数字用户名与手机号别名冲突时的确定性处理，不可猜测另一个账号。

对应仅需聚焦验证：同账号分别用用户名/手机号登录得到同一正式账号和本地 shadow；公开 DTO/token 身份不含手机号；未知或冲突号码不能落到别人的账号。若删除手机号登录扩展，则不需要这组新增兼容实现。

## B 的外部依赖边界

计划对禁止固定码、假发送、只验格式就发赠额的约束正确，不应为赶进度绕过。

- 服务商、支持号码地区、批准签名/模板和真实配置位置未确认前，可以做独立分析 A、B 的本机表单预览、验证/账务契约设计，以及只在测试进程注入传输替身的聚焦测试。不得声称已能发送或验证真实短信。
- 在 B 开始依赖服务商的实现前，补齐实际发送 API、规范化规则、验证码归属/消费方式、发送失败和超时处理，以及手机号/IP 的限额数值和可信代理 IP 来源。采用现有 DB 即可，不需要 Redis、通用风控平台或其他注册方式。
- 验证码消费、手机号唯一占用、账户、持久一次赠额记录、5000 credits 与账本必须同事务；手机唯一及赠额唯一应由 DB 约束保证。错误尝试和发送限额需持久、并发有效，不能因注册事务回滚而重置失败次数；发送网络调用不得持有用户/账务事务锁。
- 未配置提供商时发送明确 unavailable，注册不得接受未验证号码。若今天仅发布 A，应隔离未完成的 B，不把赠额默认/环境读取变更单独带入旧的无验证注册路径，也不把已展示 50 积分当成成功入账。
- B 正式上线以实际生效赠额为 5000、真实受控号码发送与验证成功、账本显示 50 积分及原账户余额未改为验收条件。未获得真实配置或测试号码时，B 记录为未完成；A 可以照常经过 TEST → PROD 发布。
