# 摆谱纠错恢复：根因与容错流程设计草案

日期：2026-10-21。版本：交互与语音修订版，尚未实施。本次 Astra Max 独立评审已完成两轮，第二轮 Approved、无阻塞项；[评审记录](../reviews/2026-10-21-baipu-recovery-interaction-review.md)保留受审版本与最后文案同步说明。旧版审核单独保留。

## 1. 目标

用户把本应落下的黑子摆成白子后，可以直接换色、先拿错子、先补旧子或先放正确的下一手；系统根据最终盘面恢复，不要求按提示的固定顺序操作。已确认的棋谱进度必须与识别基准一致，恢复后能继续落子。本次新增：提前摆好两手可自动核对；主动考虑边界；错色等问题要有清晰语音，不能只亮灯。

## 2. 本次原因：已确认与待确认的边界

棋谱 `kifu_178448`，申真谞执黑、王星昊执白，共 219 手。

- 用户确认：最初应摆黑子，误摆白子，随后纠正，并点过“摆好了，继续”。
- 日志：12:21:51 确认白棋 P8；12:21:59 确认 J8 为白色。棋谱下一手 J8 应为黑色，进入错色纠正路径符合现有实现。
- 日志：12:22:00 进入核对，`matched=114/116, missing=2, extra=1`；随后长时间 `115/116, missing=1`；12:23:38 发出 `setup_complete`。
- 浏览器实际状态：已摆 `k=115`，等待总第 116 手、白方第 58 手 P8；状态机 `await.target` 却包含 P8 白子，共 116 颗。
- 摄像头实际盘面与该 target 完全相同。棋谱第 115 手盘面与 target 唯一差别是 P8：棋谱为空，target 为白。

### 直接导致卡死的代码链

1. `usePhysicalBaipu.ts` 的 `adopt()` 把当前摄像头整盘读数作为新 target，同时保留原来的 `k` 和 `next`。
2. `physicalBaipuMachine.ts` 明确禁止 `reason=adopt` 的“已放好下一手自动推进”；收到 `SETUP_COMPLETE` 后直接用这个 target 进入 await。
3. 该 target 被送给 `expectedBoard`，后端 `MoveDetector.force_sync()` 把 P8 当作已有棋子。
4. 页面继续等 P8，识别层持续看到已有 P8，没有新的空点到白子的变化，无法产生下一次推进事件。

已用实际 TypeScript reducer 与本次矩阵复现；真实 MoveDetector 在错误基准下连续 8 帧均无新落子，改用棋谱第 115 手基准则确认 P8。用户每次点击与拿放棋子的完整顺序未被日志记录；上述状态错位和失败机制已确定，不依赖猜测点击顺序。

### 使纠错变难的因素

现有 setup 要求目标盘面完全相符；密集盘面短暂漏看一颗旧子，就会拖住恢复。“摆好了，继续”用单次整盘读数绕过核对，却把识别读数变成了新的棋谱事实。日志中的持续 missing 已确认，其具体位置当时是真缺子还是识别波动，尚无完整逐点原图可判定。

同点错色时，现有提示仍是“把该点的子拿起来，放到该点”，没有直接说需要换颜色。另有两个已读代码中的恢复风险：setup 完成事件没有目标编号，命令队列会忽略单条非灯控请求失败后继续执行。它们需要纳入新流程的保障，但没有证据证明本次发生过旧事件覆盖或请求失败。

现有测试覆盖了错色、单独撤回和 adopt 不提升，但没有把“错色 → 纠正/撤回 → 下一手已在盘上 → 点击继续 → 后续落子”连成完整验收。

## 3. 选择的方案与范围

| 方案 | 取舍 |
| --- | --- |
| 只补 adopt / 只增加报警声 | 能遮住部分故障，仍解释不了怎么改，也不能可靠识别提前两手 |
| **有限两手核对 + 明确交互与固定语音** | 推荐；覆盖日常错误与提前摆子，沿用现有离线音频，复杂度可控 |
| 全谱自动搜索 + 实时动态语音服务 | 重复局面易误跳，增加运行时依赖，本次不采用 |

不修改相机标定、模型、手/阴影判据、预览线程或其他棋类。看不清时保留进度，不把识别漏检直接称为用户摆错；本方案不声称修复所有视觉误判。

## 4. 用户如何恢复

### 4.1 以棋谱事实核对，拿放顺序自由

k 是已提交步骤，B(k) 由现有 replay 得到（包括颜色和提子），O 是摄像头证据，不能覆盖棋谱。一般恢复检查当前/未来最多两步 B(k)、B(k+1)、B(k+2)：

- 完整唯一匹配当前步：恢复等待，不改 k。
- 完整唯一匹配前一/两步完成态：worker 应用同一 canonical 基准后，页面一次写入目标手数；不要求拿起重放、逐步点确认或循环加两次手数。
- 错色直接换，错位可以先拿错子或先摆对，提子可先提后摆；只看最终合法盘面，不规定纠正顺序。
- 先摆好两手但还缺旧子/未提完：显示仍需核对的位置，处理完后再同步，不把错误收进基准。
- 窗口按真实 steps[] 构造，不从棋子数量猜手数；终局不能越界。

普通正确落子保留 MoveDetector 已有确认快路径，不每手加整盘等待。两手已完整摆好时，用原推理结果的盘面变化事件立即触发 verify，不等旧10s补救；不新增读帧或模型推理。

### 4.2 不确定时有退路

- 自动窗口不跨 pass 或无物理变化步骤；虚手沿用明确步骤流程，不能凭相同盘面跳过。
- 同一盘面对应多个候选手数：不猜最早/最晚；展示匹配手数与着法，让用户选“核对此手”，再用新鲜画面确认。
- 超过两手或用户认为进度不对：“对齐手数”可选 0..总步骤并预览盘面；选择数字不改进度，核对并实际应用成功后才保存。选错可换目标，取消/退出保留原进度；不自动搜索全谱。
- 明确撤回：先达到撤回目标，尚未拿走的旧子不能把撤回抵消。pendingUndo 随现有进度保存，重连、重核和重新进入不解除；只有目标确认或用户明确选择新的对齐目标且核对成功才能解除。
- 试下/支招：暂停识别，结束后核对目标；网络/相机暂时不可用不丢 k，恢复时重新验证，不沿用旧成功。

“重新核对”：未完成核对沿用同版，不反复清确认窗口；请求结果未知重发完整同版；已在等待状态再主动核对则建立新版本。自动补救不能打断正常一手正在累计的确认。

歧义在本版本锁定等待选择，后续盘面变唯一也不自动提交。打开选择弹窗立即冻结提交并暂停识别，保存原k/撤回意图；取消临时目标时废弃其版本，重新核对原目标后再恢复，晚到的临时成功不能生效。断线有独立“重试连接”：原hook须真正新建socket并隔离旧回调，新onopen后才start/verify；目标重核不能代替连接重试。

### 4.3 声音告诉用户具体怎么改

| 场景 | 语音 | 屏幕/灯与下一步 |
| --- | --- | --- |
| 应白实黑 | “这一手应摆白棋，请把标记处的黑棋换成白棋。” | 文字给 P8 等具体坐标，灯定位；直接换色后自动继续 |
| 应黑实白 | “这一手应摆黑棋，请把标记处的白棋换成黑棋。” | 同上，不能把黑换白/白换黑播反 |
| 确定的多子/错位 | “标记处多了一颗棋子，请取回后继续。” | 所有合法未来候选都不接受的子才称多子；摆好的合法下一手不提示拿回 |
| 旧子未核对上 | “有位置还没核对上，请检查屏幕标记处。” | 中性提示；不能确定漏识别还是缺子时不责备用户 |
| 提子未完成 | “请提走屏幕标出的棋子，拿完会自动继续。” | 只标所选合法目标实际还要拿走的位置 |
| 歧义 | “盘面对应多个进度，请在屏幕上选择已摆到的手数。” | 选目标后仍核对，不直接跳 |
| 持续不可见/识别不可用 | 中性“暂时看不清棋盘”或“识别暂时不可用” | 短暂伸手不打扰，超既有10s门槛才播不可见提醒；无证据不推断是手还是阴影 |
| 恢复/两手对齐/完成 | 各一条简短结果语音，优先完成且互斥 | 只在目标 applied 后播；普通每手仅保留落子音效 |

多处问题时屏幕可标全部，语音先说最明确的一处；该处未解决不因扫描顺序改变焦点，用户仍可任意顺序改。候选之间对颜色/操作有冲突，先通用核对，不强行指定取子或换色。

“距离最近的盘面”仅用来中性展示，不能决定取子/换色灯。所有允许候选中的正确占位都应受保护（撤回/手动对齐按唯一目标）。正确落子已经确认且有提子时，提子提示绑定该步骤的结果，不能因要提五颗而错误地让用户拿回新子。B2前缀已摆对但还有额外子，提示可对齐更多手数，不能强迫取回。

### 4.4 提醒不应变成新的干扰

- 同一稳定问题首次播一次，不随每帧/重核/重连重复；不同纠错指令至少相隔8s，只保留最新有效提示，不积攒长队；健康阻塞和实际恢复/完成可立即打断，不受该间隔限制。
- 可靠的错子确认可立即提醒；其他差异经过已有确认帧数；短暂读不清不播“摆错”。
- 问题消失、暂停、换目标或离开页面立即取消旧语音与待播计时器；成功语音也不能抢在实际应用回执前。
- 恢复卡提供“重播提示”，只重播当前有效指令，不改进度、不重新核对。
- 沿用已有“语音提示”和“落子音效”两个设备级开关；静音不自动打开。真实播放失败才显示“语音未播放，可点重播”；语音失败不阻塞识别。

不可见状态须在worker无帧/运动/几何等早退分支也产生，不依赖一次模型成功结果；不附旧盘面、不伪造新观测。短暂重复相机帧只跳过处理，持续冻结达10s才提示，带实际持续时长避免再等10s；恢复可见即取消旧timer，主动暂停不发不可见警告。仅新的摆谱HTTP与显式连接尝试设5s超时，保证共享请求队列不会永久阻塞；前端超时不等同远端未执行，仍按幂等规则恢复。

### 4.5 复用已有能力

已对照代码：摆谱页只有 stone 音效，未调用 useVoice；useVoice、audioPrefs、静态 MP3 挂载与开发时生成脚本已经存在。增加12句固定引导，开发时生成并提交、设备离线播，语音说颜色和动作，坐标由屏幕和灯提供；不新增实时 TTS 或语音识别。

目标交接继续使用 generation/revision、新鲜摄像头帧去重、raw-voted 与 reference-corrected 双矩阵核对。旧事件不能覆盖新目标，音频绝不进入阻塞识别的关键命令队列。页面进度、保存值、next 和灯依据同一次应用确认更新；末手含提子应用完才完成。
