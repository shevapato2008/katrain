# 摆谱纠错恢复：根因与容错流程设计草案

日期：2026-10-21。状态：原因调查与设计稿；配套逐步实施计划已完成两轮独立审核并按意见修订，尚未实施。第二轮最后修订未追加第三轮复审，详见审核记录。

## 1. 目标

用户把本应落下的黑子摆成白子后，可以直接换色、先拿错子、先补旧子或先放正确的下一手；系统根据最终盘面恢复，不要求按提示的固定顺序操作。已确认的棋谱进度必须与识别基准一致，恢复后能继续落子。

## 2. 本次原因：已确认与待确认的边界

棋谱 `kifu_178448`，申真谞执黑、王星昊执白，共 219 手。

- 用户确认：最初应摆黑子，误摆白子，随后纠正，并点过“摆好了，继续”。
- 日志：12:21:51 确认白棋 P8；12:21:59 确认 J8 为白色。棋谱下一手 J8 应为黑色，进入错色纠正路径符合现有实现。
- 日志：12:22:00 进入核对，`matched=114/116, missing=2, extra=1`；随后长时间 `115/116, missing=1`；12:23:38 发出 `setup_complete`。
- 浏览器实际状态：已摆 `k=115`，等待总第 116 手、白方第 58 手 P8；状态机 `await.target` 却包含 P8 白子，共 116 颗。
- 摄像头实际盘面与该 target 完全相同。棋谱第 115 手盘面与 target 唯一差别是 P8：棋谱为空，target 为白。

### 直接导致卡死的代码链

1. `usePhysicalBaipu.ts` 的 `adopt()` 把当前摄像头整盘读数作为新 target，同时保留原来的 `k` 和 `next`。
2. `physicalBaipuMachine.ts` 明确禁止 `reason=adopt` 的“已放好下一手自动推进”；收到 `SETUP_COMPLETE` 后直接用这个 target 进入 await。
3. 该 target 被送给 `expectedBoard`，后端 `MoveDetector.force_sync()` 把 P8 当作已有棋子。
4. 页面继续等 P8，识别层持续看到已有 P8，没有新的空点到白子的变化，无法产生下一次推进事件。

已用实际 TypeScript reducer 与本次矩阵复现；真实 MoveDetector 在错误基准下连续 8 帧均无新落子，改用棋谱第 115 手基准则确认 P8。用户每次点击与拿放棋子的完整顺序未被日志记录；上述状态错位和失败机制已确定，不依赖猜测点击顺序。

### 使纠错变难的因素

现有 setup 要求目标盘面完全相符；密集盘面短暂漏看一颗旧子，就会拖住恢复。“摆好了，继续”用单次整盘读数绕过核对，却把识别读数变成了新的棋谱事实。日志中的持续 missing 已确认，其具体位置当时是真缺子还是识别波动，尚无完整逐点原图可判定。

同点错色时，现有提示仍是“把该点的子拿起来，放到该点”，没有直接说需要换颜色。另有两个已读代码中的恢复风险：setup 完成事件没有目标编号，命令队列会忽略单条非灯控请求失败后继续执行。它们需要纳入新流程的保障，但没有证据证明本次发生过旧事件覆盖或请求失败。

现有测试覆盖了错色、单独撤回和 adopt 不提升，但没有把“错色 → 纠正/撤回 → 下一手已在盘上 → 点击继续 → 后续落子”连成完整验收。

## 3. 方案比较

| 方案 | 用户体验与代价 | 结论 |
| --- | --- | --- |
| 修补 adopt，避免把下一手吞入基准 | 改动最小，可修本次死锁；仍有多种恢复入口和旧结果串入的问题 | 可作为最小缺陷修复，不能完整覆盖本次流程目标 |
| 统一按棋谱当前/下一手盘面重新核对 | 拿放顺序自由；统一处理错色、错位、先放下一手、撤回和重复点击；范围可控 | **推荐** |
| 在全谱中自动寻找任意匹配局面 | 可跳很多手，但提子、虚手、重复局面会产生歧义，易误跳进度 | 本次不采用 |

## 4. 推荐流程：看最终盘面，自动找回当前进度

### 4.1 一份棋谱事实，三种不同的数据

- `k`：已经确认的棋谱进度。
- `B(k)`：用现有棋谱回放函数得到的该步合法盘面，含正确颜色和提子结果。
- `O`：摄像头读数，用来提供证据，不能直接覆盖 `B(k)`。

恢复时同时识别两个候选：当前盘面 `B(k)`，以及下一步完成后的盘面 `B(k+1)`。本轮默认不根据缺子自动倒退进度，也不跨多手自动跳谱。用户明确点“撤回”时，必须先稳定核对撤回后的 `B(k)`；这之前禁止接受 `B(k+1)`，否则盘上尚未拿走的旧棋子会立刻撤销撤回操作。该限制随现有进度记录保存，在重复核对、暂停恢复、重连和重新进入页面时继续有效，直到撤回目标得到确认。虚手、AE 和 SGF 摆子步骤继续遵循已有 steps[] 语义，不从棋子数量推断手数。

### 4.2 自由纠正，系统持续核对

| 用户的实际操作 | 系统应做什么 |
| --- | --- |
| 黑子误摆白子，直接换回黑子 | 正确棋子获得稳定确认后，自动接受该手，继续下一手 |
| 先拿走错子，停一会儿再摆正确棋子 | 拿走后回到等待当前手；摆对后自动继续 |
| 先放对的位置，再拿走错位置的棋子 | 暂存“下一手已看到”的候选；多余棋子移开、旧盘面核对通过后推进一次 |
| 先放下一手，再补回误碰掉的旧子 | 保留当前进度；补齐后若完整匹配下一手完成态，自动推进一次 |
| 完全摆回出错前盘面 | 恢复等待当前手，已确认进度不丢失 |
| 下一手已经摆好，又点“重新核对” | 识别出它是下一手完成态，推进一次；不会要求拿起重放 |
| 下一手位置正确但颜色仍错 | 保持纠正提示，不推进；直接换色即可 |
| 明确撤回 | 先拿走被撤回的棋子、恢复指定目标盘面，再恢复正常下一手识别；不能自动把撤回操作抵消 |
| 试下或收起支招 | 沿用同一核对入口，使用相应棋谱目标；旧结果不能恢复旧目标 |

涉及提子时，用 steps[] 给出的 removed 清单判断；恢复过程中允许先落子再提子、或先提子再落子。相关棋子尚未处理完时显示“还需拿走/补回”，本次恢复不以未完成的物理盘面提交下一步。普通摆谱原有提子流程不在本次设计中另算一套棋规。

### 4.3 完成恢复时，一起更新进度和识别目标

恢复决定必须是同一份结果 `{k', B(k'), recovery_id}`：

1. 对本次目标获得有效的新鲜识别证据，确定恢复到 k 或接受 k+1。
2. 暂停接收本轮重复落子，串行同步对应的识别基准；确认该目标已实际应用，不能只以 HTTP 请求入队成功为准。
3. 对同一个 recovery_id 最多提交一次手数与保存进度，然后恢复等待并点下一手。
4. 同步失败时停在“正在恢复”，保留棋谱和用户进度；重试同一决定，不先显示成功，也不无条件点下一手。

正常等待状态的识别基准必须与已确认的棋谱步一致；当前尚待接受的下一手，不能仅因进入恢复而成为“已完成”的基准内容。

所有摄像头推进都在 worker 应用确认后提交。普通落子沿用已有 MoveDetector 确认，只做 canonical 目标交接，不额外等新帧或整盘核对。末手也先完成目标应用、再进入完成页并清进度，避免提前关闭识别。确认与下一手事件同批抵达时，暂缓消费下一条，等页面进度同步后继续处理，不能当噪声丢掉。

复用现有 reducer、串行命令队列及进度保存，不引入新的业务会话服务或持久化系统。采用仅供摆谱使用的目标同步接口：服务代号隔离页面生命周期，目标版本隔离纠错/撤回，worker 实际应用基准后才发完成事件。旧 setup 接口保持兼容；不会把无编号的旧完成事件包装成本轮结果。具体字段与执行顺序见配套实施计划。

### 4.4 识别不清时，保持核对

复用已有多帧投票、参考检查、遮挡/运动门控和置信度策略。核对的是处理后的稳定盘面，不要求原始图像单帧完美；本轮不增加跨时刻拼接整盘的新缓存，也不调整识别模型、阈值或阴影判据。正常落子保留现有确认快路径；仅纠错核对使用现有确认帧数配置，重复点击不重置窗口。

- 明确看见的错色、多子、缺子继续给出对应位置提示；持续确认的真实差异必须处理。
- 手遮挡、运动、低可信读数或旧帧保持“正在核对”，不能据此覆盖棋谱、推进或自动撤回。现有识别无法区分真缺子与未看清时，界面只说“还需核对”，不声称用户一定漏摆。
- 新核对目标只使用目标建立后采集的不同摄像头帧；清理该核对窗口的旧平均/投票累积，保留几何和既有参考检查能力。稳定投票读数和参考检查后的读数须同时符合候选，真实缺子不能被历史拼盘掩盖。普通摆谱也在平均/投票/确认之前去重相机帧，不用相同画面重复累计。
- 盘面仍有差异时保留核对，不以前端计时忽略差异。持续漏识别仍可能拖慢恢复，这是识别能力的边界；本方案消除错误基准造成的永久等待，不声称解决所有视觉漏检。
- 超时显示仍需核对的位置，允许用户任意顺序调整后“重新核对”；按钮不会绕过真实差异。

### 4.5 “摆好了，继续”改为“重新核对”

按钮只请求一轮新的有效核对，不采用整盘快照作为新基准，不无条件推进。无论自动核对还是按钮触发，都走同一个恢复决定。

正在核对或等待回执时，重复点击沿用本版，避免清掉累积；已经恢复等待后主动点击则建立新版本核对，不能只返回旧的完成回执。核对超时、同步错误或等待超过 10s 时，现有动作区提供该按钮。自动补救有正常落子正在确认时取消，用户主动核对入口仍可用。

日常提示尽量短：

- “J8 需要黑子，换对后自动继续。”
- “正在核对盘面，可按任意顺序改正。”
- “已纠正，继续第 118 手。”

已正确放下的下一手不闪蓝灯要求移除，也不要求重新拿起（明确撤回的场景须先达到撤回目标）。不能把尚未核对通过显示成恢复成功。保留明确撤回、试下和退出入口，不用弹窗规定拿放顺序。

恢复后若下一手已在盘上却迟迟没有落子事件，10s 后用现有只读盘面快照检查一次；只有完整符合合法下一手完成态才触发带编号的新鲜核对。快照不作完成证据，正常思考时仍保持下一手灯。重复核对不反复重置确认窗口，不新增图像推理任务。

## 5. 必须通过的验收

1. 本次真实第 115/116 手 P8 状态和黑棋 J8 错色触发序列；最终正确时恢复到唯一正确的步数，并能继续再摆至少两手。
2. 黑棋放白子后直接换色、先拿后放、先放对再拿错、先放下一手再补旧子，结果一致。
3. 下一手已在盘上时重复点击核对、多次收到完成事件，最多推进一次；颜色错时零次推进。
4. 提子未拿完不能把错误盘面当作完成；旧子真实缺失不能被缓存掩盖。
5. 手遮挡、旧帧、暂时掉帧只延迟核对，不改变棋谱，不永久锁住；可靠画面恢复后可继续。
6. 核对中撤回、试下恢复、网络重连、旧请求迟到，不发生旧结果覆盖新目标。
7. 手数、保存进度、识别基准、下一手和灯指向一致；失败时状态可理解、可重试。
8. RK3562 做一次真实错色纠正与已放下一手的恢复验收，记录恢复耗时和成功后的连续推进；保留原正常摆谱回归。
