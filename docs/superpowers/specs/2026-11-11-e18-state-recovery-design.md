## Goal and scope

The electronic board, history and turn must show move 16 / Black to play; the next legal Black move (move 17) must work. Restoration never submits another White move. Recovery must show pending, success or a retryable error honestly and must not repeatedly reopen an identical stale dialog.

## Minimal design

### Serialize local snapshot publication; do not order by node depth

Extend the existing runtime `ai_ladder_commit_lock` across `_broadcast_current_state`'s fresh `get_state()` and synchronous state callback/scheduling. Release it before post-broadcast hooks and before any socket I/O. A snapshot cannot be captured at 15, allow the commit/publication of 16, and then publish 15. Legitimate undo, redo and navigation remain valid because there is no depth comparator or new state-version framework. Callback order alone does not prove socket order: `SessionManager._schedule_broadcast` must use one `loop.call_soon_threadsafe` task-creation path for both loop and background callers. The queued creation callbacks then retain publication order. Serialize `_broadcast_payload` with one per-session async send lock, so yielding sends to multiple sockets cannot interleave payload order; no I/O occurs under the game commit lock. Use this scheduling path for state and matching sound payloads, preserving state-before-sound ordering.

Keep the existing throttle lock limited to throttle bookkeeping; release it before acquiring the commit lock. The callback chain `_on_state → _schedule_broadcast` schedules asynchronous sends without awaiting; the physical-play wrapper schedules to its loop when necessary. Do not add acquisition of `session.lock` in this callback. Existing mutation order is `session.lock → ai_ladder_commit_lock`; service metadata is acquired after commit and must never acquire game/session locks in reverse. Audit `on_session_state` hooks and existing post-broadcast move-sound callbacks before landing. Test serialized publication with real barriers and bounded joins, including a contending legitimate navigation. Add the actual asyncio scheduler schedule where old background15 enqueues before newer on-loop16 without yielding; assert fake sockets receive `[15,16]`, not merely that callbacks ran in that order. Include yielding multi-socket delivery and matching sound ordering.

`session_state_for_read` returns a fresh runtime snapshot for local sessions, and uses the central mirror for `pvp_lobby`. Construct a response copy, preserve the existing `legacy_analysis_allowed` / `strip_private_analysis` rules and response metadata, and never write that projection back to `session.last_state`. Preserve timer freshness and privacy/billing restrictions. No request-specific filtering belongs in the canonical cache.

### Use current authority for the normal vision turn check

Replace the ordinary/non-ranked cached `last_state.player_to_move` precheck with a live local next-player read under the existing commit lock; use the central mirror for `pvp_lobby`. Recheck the captured binding/session/game generation before acting. Keep the final guarded play and its live turn/AI/endgame checks. A stale cache saying W cannot reject B17 after live W16. Do not bypass human-seat guards or allow physical White input on the AI seat.

### A scoped restoration operation, preserving legacy reset semantics

Extend the existing `/api/v1/vision/sync/reset` request with optional `session_id` and `game_id`. The mismatch UI supplies both; this opts into a bound-game restoration path. Both identity fields must be supplied together; a partial scoped request is 400/422 and must never fall through to legacy reset. Existing unscoped digital reset and `adopt=physical` retain their behavior, including RESET_SYNC's digital∪physical detector baseline. Do not alter that baseline or reference invalidation policy in task A.

The scoped restoration path deliberately uses the existing `SET_EXPECTED_BOARD(force_rearm=True)` publication, not RESET_SYNC. Its purpose is to reconcile the currently authoritative board, not to adopt observed extras or invalidate references. This prevents a legal, already-present B17 from being silently absorbed into a reset union. The existing detection path owns any new move; restoration itself never calls `play`.

Under the commit lock: validate the captured vision binding source, runtime game object and requested game ID; obtain fresh authority; synchronously publish the same snapshot to the canonical/UI callback; reconcile the planner to that snapshot and remove only the existing lag/removal recovery gate appropriate to this path. Do not clear game-over, hint, USB, geometry, engine-error or remote-disconnect gates. Enqueue fresh expected via the existing source/generation guards. Release all thread locks before waiting.

One active scoped restoration per bound game is sufficient. Generate an opaque `recovery_id` and register its waiter before enqueueing. Carry it on SET_EXPECTED_BOARD and on the sync state's pending exact-match acknowledgment. Normal expected publications during this same recovery carry the same ID with their current node/revision, so a legitimate B17 can advance normally and the waiter follows the current same-game position. Emit acknowledgment only from a processed exact-equality frame, not from status=`synced`, reset, legacy unversioned events or a stale queued event. This adds acknowledgment metadata only; stone classification and confirmation rules do not change.

Observe acknowledgments in `VisionService._drain_worker` without stealing them from the normal vision pump. Match recovery ID, binding epoch, expected revision and node. One waiter/future, cleaned on success, failure, unbind, replacement or timeout, is enough; do not add a general recovery framework. Bound the whole operation to eight seconds using one original deadline. Revalidate the same binding/game and current node/revision after acknowledgment before success; a newer same-game expected position continues within that deadline. Retain and recheck an already-arrived matching newer acknowledgment when advancing the target; do not discard it and wait for an event that was already consumed. Rebind/replacement or conflicting request is HTTP 409; unavailable worker is 503; timeout is 504. No false `{ok:true}`.

Success returns `{ok:true,recovery_id,session_id,game_id,current_node_id}`. The UI refreshes through an owning `useGameSession` method using existing `API.getState(sessionId, token)`, so privacy filtering stays on the normal route. The hook captures a local receive-generation before GET and advances it synchronously whenever an authoritative state is accepted (including WebSocket updates, session/game replacement and legitimate undo/navigation). A response whose generation was superseded must not overwrite current state. It also must not count as an applied recovery refresh: success may use the already-applied same-game current state only if its node matches the exact verified recovery result; otherwise return a typed superseded result, keep one retryable “局面已变化，请重新核对” dialog, and require a fresh scoped verification. Bound HTTP refresh with a two-second request deadline; do not introduce depth comparison, automatic unbounded retries or a generic revision framework. The eight-second worker-verification deadline remains one original deadline. A game that advanced legitimately is accepted at its new current node; there is no expectation that the stale UI node ID equal the recovery target.

### Existing UI, honest feedback

Reuse BoardMismatchDialog, its buttons and caption/error text. While a scoped restoration and state refresh are pending, keep one dialog visible, disable repeated taps and show “正在核对盘面…”. A network error, timeout or wrong-game response leaves a retry action and explicit error; it must not claim success or suppress all future actionable differences. Coalesce identical incoming mismatch events into that visible operation. On success apply fresh state before clearing the dialog. Ignore responses after session/game changes.

Automatic physical restoration without a tap also matters: any `synced` event while a mismatch is active is only a trigger for the same coalesced scoped verification and fenced refresh operation used by the button. It is never evidence of completion, and the reducer must not clear this mismatch on a bare event. A stale or placement-pending-only synced event can start checking, but cannot clear the dialog after GET alone. A newly processed exact frame carrying the current recovery ID can complete without a button tap, even if the old node acknowledgment was consumed earlier. Repeated triggers share the single in-flight operation; a failed operation stays retryable instead of creating an automatic retry loop.

Use refreshed `player_to_move` for the existing single-extra adopt button: one extra Black stone is adoptable only when it is actually Black's human turn; missing E18 never offers adopt. Do not silently adopt or deny a physical stone. Existing captures, pending platform moves, phantom-denial and local-confirmation ownership remain intact.

2. Cache W / live B after White E18 accepts legal Black move 17 exactly once, while AI-turn and wrong-game input remain rejected.
3. A delayed recovery GET16 after WebSocket17 cannot replace17 or falsely complete; a received legitimate undo is equally protected. Physical E18 restoration reconciles node16 without calling play. Success requires current exact observation plus coherent refreshed UI; stale ack, bind/game change, absent worker and timeout cannot return success.
4. Bare/placement-only synced cannot dismiss a mismatch; an actual exact-restored frame completes the same automatic scoped path without tapping. A pending next Black stone is neither lost in a union baseline nor committed by restoration; ordinary confirmation submits it once and recovery follows the resulting current position.
5. Focused existing privacy, post-broadcast sound, routing, capture/phantom, binding and recovery tests pass. No full GPU test or broad new infrastructure is required.
