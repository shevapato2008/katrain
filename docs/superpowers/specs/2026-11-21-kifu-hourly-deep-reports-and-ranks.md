# 星阵职业棋谱小时导入、深度报告与段位修复

## 现状

TEST 的 `kifu_ingest` 每小时从星阵公开棋谱源 `19x19` 拉取棋谱，在 TEST 发布和验证后，由现有受限通道交给 PROD 接收。正式站最近五盘样本均返回 `has_analysis: false`。三星杯样本 `179180` 和野狐训练赛样本 `179183` 的报告接口均返回 `unavailable`、`analyzed_moves: 0` 且没有参数错误；历史样本 `24171` 返回 `completed`、211 手和 2,000 请求 visits。网页仅在后端确认完整深度报告时展示报告入口。现有分析能力曾用于显式批次；小时导入没有自动创建深度任务。现行生产 worker 开关尚未从容器核实。

正式站 `179180` 两侧段位缺失，返回 `historical-rank-as-of-v1` 和 `untrusted_target_date`，说明新谱已经经过历史段位规则。公开 API 足以证明该盘被规则留空，不能据此推算全库待修数量。

## 要交付的行为

1. 启用后，每一盘由小时任务新建入库的星阵职业棋谱进入深度分析。采用现有固定 KataGo 模型，为主线每个局面请求 2,000 visits，包括初始局面，通过现有职业报告读取和展示。重放、重复来源、历史已入库棋谱以及已有任务或报告的同一身份不会新建任务。已有历史报告继续可读，历史棋谱不做分析回填。
2. 导入流程提交持久分析任务，后台 worker 消费。引擎暂时不可用时，分析 worker 自行退避并从最后完成的局面继续。普通用户报告和高优先级实时分析沿用已有优先级。SGF 无法可靠复盘、或贴目/规则无法依照已批准策略解析时，记录可追踪的原因，待补证后按现有人工准入路径处理。小时采集不等待 GPU；重复发布不会重新分析。
3. 用现有历史段位工具对 TEST 和 PROD 的全部历史棋谱进行只读盘点。按对局日期匹配同一棋手在当时或之前最新的可靠原始证据。规范可确认的段位、补齐可证实的缺失值并修复可证实的错误。原谱、原字段和历史发布回执保留；无法核实的槽位保留真实原值或待核。修复按冻结清单分批，记录已修改、未变化和拒绝的数量及原因。已冻结的 v3 段位同样复核。若可靠证据支持更正，使用能保留现有发布回执和重放的修复路径；在找到安全写入路径前将这些差异列为验收未完成。
4. 小时入库继续对新棋谱的黑白双方执行同一套资格规则。已有 v3 段位冻结路径直接复用，验证标准化、缺值补齐、来源与身份冲突、日期不足以及 TEST 至 PROD 重放。现有规则无法确认的日期或段位不以网页显示的比赛日期或棋手今日段位直接覆盖。后续有可靠证据时，通过现有审定流程修正相应槽位。

## 验收和发布

- 测试覆盖新入库、重放、已有报告、异常 SGF、不合格段位、可靠证据补齐和双环境使用各自 ID。
- 排队启用前校验两端实际 worker/模型配置与公开报告 API。发布后验证真实新入库棋谱有任务，至少一局在 TEST 和 PROD 分别完成 2,000 visits 报告并可从 Galaxy 打开。保留旧报告作为对照。
- 段位修复先盘点两库；在 TEST 分批应用及复核，再处理 PROD。验证代表性历史修复和真实新谱的段位、来源及待核原因。用现有撤销流程保留精确补偿能力。
- 按 `fix/kiosk-ui-debug` 追最新 `develop`、验证和推送、合入并推送 `develop`、更新并推送 `smartbox-software` 的 `main` 上的 `vendor/katrain` 指针、部署 `home-ubuntu` 和 `ucloud-v100` 的顺序执行。实体盒端不发布固件或应用版本。
