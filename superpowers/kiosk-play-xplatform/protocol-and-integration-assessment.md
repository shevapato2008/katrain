# 野狐 FoxWQ 接入 — 协议要点 + 工程量评估

- **日期**：2026-07-12
- **依据**：一手通读官方两份文档 —— `野狐围棋AI接入协议` v1.05(9 页)+ `野狐围棋AI接入手册` v2.01(22 页)，以及 `ReadMe.txt` / `gtp2 中文手册`。
- **用途**：本轨（`feature/kiosk-play-xplatform`）野狐分支的设计蓝图。官方包(含这两份 PDF)已 `.gitignore`，随时可从 `https://www.foxwq.com/Public/Soft/aiProgramAndManual.zip` 重下。

---

## 0. TL;DR

1. **架构是三段式**：`野狐 Windows 客户端 ⇄(TCP, 野狐私有协议)⇄ Controller ⇄(GTP)⇄ 引擎`。客户端**不支持** GTP 直连，必须经一个 Controller 中转。
2. **最大约束（一手文档才看得到）**：**野狐 Windows GUI 客户端必须在环，且"所有对弈逻辑由客户端完成"**。它是登录 AI 认证账号、真正在野狐服务器上对弈的那一环，Linux ARM kiosk 跑不了它 → **必须有一台 Windows 主机在环**。这跟 Golaxy(纯 REST 隧道)、OGS(纯 API)有本质区别，网络调研阶段看不出来。
3. **两条集成路径**：
   - **Path A**：用官方 `FoxGTP.exe` 当 Controller，我们后端实现一个 **GTP 引擎适配器**。协议工作量**小**（我们已会 GTP），但 FoxGTP 是 Windows 程序。
   - **Path B**：自研 Controller，直接实现野狐 `$FA/$AF` 私有协议。协议工作量**中**，但 Controller 可跑在纯 Linux 后端，架构与已跑通的 Golaxy 适配器几乎同构。
4. **human-relay 的真正拦路虎不是协议，是两件事**：
   - **时间控制**：引擎 `genmove` 秒级返回，真人在物理棋盘要几十秒~几分钟；野狐快棋读秒(如 30s)会**超时判负**。→ 只能玩慢棋，且要用官方"自动接受对局邀请"过滤器限定长时限。
   - **合规定性**：野狐 AI 接入是给"AI 引擎"的；我们拿 AI 认证账号转发**真人**落子(human-relay)是否被接受，**必须先问 `ai@foxwq.com`**。
5. **还有第三条路 Path C（手机 App 中继）** —— 阿尔法蛋 / 元萝卜这类围棋机器人走的就是它，**能免掉那台 Windows**。但调研核实(2026-07-12)：它们的干净版**本质是野狐官方商务合作**（设备级授权/扫码配对），**没有自助技术版本**；不谈合作只剩 App 自动化（踩 ToS、封号高、只配做 Demo）。详见 §7.5 / §7.6。

## 1. 通信架构（三段式）

```
 野狐服务器
     ▲
     │ (野狐自有账号/对弈, 全部对弈逻辑在此)
     │
┌─────────────┐   TCP/IP        ┌──────────────┐    GTP       ┌───────────┐
│  Fox Client │ ◀───────────▶  │  Controller   │ ◀────────▶ │  引擎/我们 │
│ (Windows)   │  野狐私有协议    │ FoxGTP 或自研  │  GTP2 命令  │  的适配器  │
└─────────────┘  $FA*/$AF*      └──────────────┘  stdio/TCP   └───────────┘
   必需·Windows                    可替换                       我们实现
```

| 段 | 协议 | 谁实现 | 能否替换 |
|---|---|---|---|
| Fox 服务器 ⇄ Fox 客户端 | 野狐内部(不公开) | 野狐 | ❌ 客户端是唯一合法入口 |
| Fox 客户端 ⇄ Controller | 野狐 AI 接入协议(`$FA*`/`$AF*`, TCP) | 野狐(客户端侧) + 我们或 FoxGTP(Controller 侧) | Controller 侧**可自研替换** |
| Controller ⇄ 引擎 | **GTP**(带 id) | FoxGTP + 我们的引擎 | 仅在 Path A 存在 |

> 文档原文：「野狐围棋客户端不支持 GTP 协议直接与 AI 引擎通信，必须通过一个控制器(Controller)进行中转」「所有的对弈逻辑由野狐围棋客户端完成」「可以根据野狐围棋 AI 接入协议文档自行开发…替换 FoxGTP」。

**关键推论**：无论 Path A/B，**Fox Windows 客户端都省不掉**——它是登录账号、在野狐服务器上真正落子的一环。我们能替换的只有 Controller，替换不了客户端。

## 2. 我们的映射（human-relay，也天然支持真 AI 对弈）

我们的"引擎"= **物理棋盘上的人 + 视觉识别 + LED 引导**：

| GTP / 野狐语义 | 我们的实现 |
|---|---|
| `genmove <color>` / 轮到我方落子($FAMOVE 字段1=1) | **阻塞**，等视觉识别到人在物理棋盘落子 → 返回该坐标 |
| `play <color> <vertex>` / 对手落子($FAMOVE) | **驱动 LED** 在物理棋盘指引对手落子点 |
| `clear_board` / 新对局($FASTATUS 无落子序列) | 复位棋盘状态、清 LED |
| `final_score` / $FASCORE | 返回点目结果（或走"同意对手点目"自动处理） |
| 认输 | $AFGIVEUP / 用户在 UI 触发 |

这套映射与 Golaxy 物理对弈闭环（`project_kiosk_golaxy_physical_play`）**同构**：都是"协议适配器 + genmove 阻塞在视觉 + 落子驱动 LED"。若把"引擎"换成真 KataGo，则天然得到"野狐真·AI 对弈"能力。

## 3. 协议要点 A — GTP 层（Path A：用官方 FoxGTP）

FoxGTP 只用到这些 GTP 命令，我们的适配器实现它们即可：

```
quit  clear_board  boardsize  time_settings  komi
set_free_handicap  time_left  play  genmove  final_score  protocol_version
```

- **必须支持带 id 的 GTP**：FoxGTP 发 `1 clear_board`，引擎须回 `=1`（回显 id）。标准 GTP 引擎(KataGo)本就支持。
- **通信方式**（手册 4.4.4）：`Standard I/O`(FoxGTP 以子进程起本机引擎，最常用) / `TCP: FoxGTP→引擎` / `TCP: 引擎→FoxGTP`。**跨机(引擎在 Linux)就用 TCP 模式**，把我们的适配器暴露成 TCP 服务/客户端。
- **读秒**（手册 4.4.1/4.4.2）：可设"围棋常用读秒规则(次数制)"而非 GTP 加拿大制；可设"数据传输消耗时间"、"引擎读秒时间"。对 human-relay 这些都要调到最宽松，但**根本受限于对局本身的时间设置**。
- **异常恢复**（协议前言）：出异常时野狐会触发引擎重初始化(重发 `clear_board` 等)；**要求引擎在计算状态下不丢弃输入的 GTP 命令** → 适配器必须把命令**排队**，不能在"等人落子"时吞掉后续命令。

> 我们已在 KataGo/Golaxy 上用 GTP，这一层**工作量小**。

## 4. 协议要点 B — 野狐 `$FA/$AF` 层（Path B：自研 Controller）

### 4.1 包格式（协议 §3.1）
```
$ABXXXX , ddd , … , ddd *hh <CR><LF>
```
- `$` 起始 + 命令字；字段用**逗号**分隔；`<CR><LF>`(\r\n) 结束。
- `*hh` 为校验位：`hh` = `$` 与 `*` 之间**所有字节的异或**，16 进制(不分大小写)。附录一给了 C++：`checkSum ^= pDataBuf[i]`。
- 内容项数量不固定，按命令解析。

### 4.2 坐标格式
每个落子 `n~xx~yy~s`（文档用 `˜` 作子分隔符）：
- `n` = 手数（从 1 开始）
- `xx` = X 坐标 **0–18，左→右**
- `yy` = Y 坐标 **0–18，上→下** ⚠️
- `s` = 棋子颜色 `B`/`W`
- 空盘/无落子表示为 `0^0^0^N`

> ⚠️ **坐标帧**：Y 是**上→下**（与 Golaxy 的 row 同向；与 GTP 的 `A1` 左下角原点相反）。复用我们踩过的坐标帧教训（golaxy 那次 `coordinate-frame lesson`），落地前务必对齐物理棋盘方向。

### 4.3 命令速查

**FOX → AI（我们要解析）**
| 命令 | 含义 | 关键字段 |
|---|---|---|
| `$FASTATUS` | 当前对局状态 | 1:是否对弈中 · 2:AI 执子色 · 3+:落子序列 |
| `$FAMOVE` | 最后一手 + 是否轮到我 | 1:是否轮到 AI(1=是) · 2:AI 色 · 3:落子`n~xx~yy~s` |
| `$FASKIP` | 停一手 | 1:是否轮到 AI · 2:AI 色 |
| `$FARULE` | 对局规则 | 棋盘/保留时间(s)/读秒时间(s)/读秒次数/贴目×100(650=6.5目)/让子序列 |
| `$FATIMELEFT` | 剩余时间 | 保留时间/读秒时间/剩余读秒次数 |
| `$FARESULT` | 对局结果 | `W+350`(3.5目)/`W+R`(中盘)/`0`(和) |
| `$FASCORE` | 请求 AI 点目 | 1:是否对手申请点目 |

**AI → FOX（我们要发送）**
| 命令 | 含义 | 关键字段 |
|---|---|---|
| `$AFPLAY` | 我方落子 | 色 + `n~xx~yy~s`，**n 必须 = 盘面最后一手 +1** |
| `$AFSKIP` | 我方停一手 | AI 色 |
| `$AFGIVEUP` | 认输（任何时候可发） | AI 色 |
| `$AFSTATUS` | 查询盘面（经 $FASTATUS 回） | AI 色 |
| `$AFSCORE` | 上报点目结果 | `error`=不支持 / `0`=和 / `W+350` |

- **轮次判断**：只在 `$FAMOVE`/`$FASKIP` 字段 1 = 1（轮到我）时发 `$AFPLAY`/`$AFSKIP`。
- **让子局**：`$FARULE` 让子序列(色只可能是 B) → 先在物理棋盘摆黑子并同步。

> 这层是个 9 页说清的小型文本协议，**工作量中等**，且与 Golaxy 适配器高度同构。

## 5. 关键约束与坑（工程必须处理）

1. **Windows 客户端在环（硬约束）** — 部署选项：① 用户自己的 Windows PC（PoC / 单板最省）；② 云 Windows VM（生产，按活跃对局池化）；③ 迷你 Windows 主机随棋盘出货。Wine 跑 Fox 客户端**未验证**，别当方案。这条直接影响 BOM / 运维模型，需产品决策。
2. **AI 认证前置** — 账号须先申请 AI 接入权限（在线网管 / `ai@foxwq.com`），否则客户端右上角无 AI 按钮。
3. **时间控制 = human-relay 最大风险** — 引擎秒级 vs 人类分钟级。对策：用手册 §5.3「自动接受对局邀请」过滤器，**仅接受**「指定保留时间及读秒范围内」「认证账号」「指定段位/时段」的**慢棋**。→ human-relay 只适合长考/慢棋，快棋不可行。
4. **禁止手动落子** — 勾「AI 连接后禁止手动落子」（人只在**我们的物理棋盘**落子，不点 Fox 客户端棋盘，防误触）。
5. **数子/规则** — 勾「AI 连接后使用中国数子规则」；点目可设「同意对手的点目申请和 AI 获胜结果」自动处理；Path B 需实现 `$FASCORE→$AFSCORE`。
6. **计算中不丢命令** — 适配器必须命令排队（见 §3 异常恢复）。
7. **断线恢复** — 有「断线自动重连」「异常崩溃自动恢复」等选项；⚠️ **QQ 账号登录没有"崩溃自动恢复"选项**（选账号体系时注意）。
8. **坐标帧对齐** — 见 §4.2，Y 上→下，复用既有坐标帧经验。

## 6. 合规（P0 阻塞，必须先问 `ai@foxwq.com`）

- 野狐 AI 接入通道**面向"AI 引擎"**。我们用 AI 认证账号转发**真人**落子(human-relay)是新形态，野狐是否接受 / 是否判违规，**必须先确认**。
- 反面路径（逆向常规客户端、注入点击 = openfoxwq 那类）**明确违反 ToS**，不走。
- 结论：官方 AI 接入是唯一干净路径，但 human-relay 定性需野狐拍板。**咨询邮件草稿已备**（问合规 + 时间控制 + 账号是否限制排位/段位）。

## 7. 工程量评估（两条路径对比）

| 维度 | Path A：官方 FoxGTP + GTP 引擎适配器 | Path B：自研 Controller($FA 协议) |
|---|---|---|
| 协议开发量 | **小**（复用现有 GTP） | **中**（实现 ~12 条 `$FA/$AF` + 异或校验 + 坐标） |
| 运维 | 需 Windows 跑 **Fox 客户端 + FoxGTP** | 需 Windows 跑 **Fox 客户端**（省掉 FoxGTP） |
| kiosk 后端 | 当"引擎"，隔一层 FoxGTP | 直连客户端，控制力更强 |
| 纯 Linux 后端 | ❌（FoxGTP 是 Windows） | ✅（Controller 可在 Linux/kiosk 后端） |
| 复用 Golaxy 架构 | 中 | **高**（几乎同构） |
| PoC 速度 | **快**（现成 FoxGTP，一台 Windows 即可端到端） | 慢（先写协议） |

**推荐两阶段**：
- **PoC 用 Path A** —— 一台 Windows PC 跑 Fox 客户端 + FoxGTP，FoxGTP 用「TCP: 引擎→FoxGTP」或「FoxGTP→引擎」模式接我们 kiosk 后端的 GTP 适配器。**最快打通端到端**，用来验证真正的两个风险（时间控制、合规），而不是先埋头写协议。
- **生产迁 Path B** —— 自研 Controller，纯 Linux 后端、去掉 FoxGTP 这层，但 **Windows 客户端仍需托管**。仅在 PoC 验证"值得做 + 野狐认可"后再投入。

## 7.5 Path C — 手机 App 中继（阿尔法蛋 / 元萝卜走的路）

> 调研结论（2026-07-12，6 角度搜索 + 对抗性核验，65 agent）。起因：用户展示阿尔法蛋 2025-05 后新推出的"对接野狐围棋手机 App"方式，问我们能否类似复刻。

**它们接的是野狐手机 App，机制是「官方设备级合作」，不是 App 自动化，也不是 PC 的 `$FA/$AF`：**
- **直接证据**：野狐官方新闻 `foxwq.com/news/16711.html` 称阿尔法蛋"人人对弈·联网对弈"权限**"仅与设备有关，与阿尔法蛋棋手账号、野狐 VIP 均无关"** → 授权**绑定在硬件上**（设备白名单）。这是"厂商×野狐官方合作"的签名特征——脚本操控用户账号会绑**账号**，不会绑**设备**。
- **类比佐证**：「元萝卜野狐围棋版」（商汤 SenseRobot）是官方**联名产品**，用户登录自己野狐账号后在 App 内生成二维码 → 靠近机器人扫码完成**设备配对绑定**，官方明确"非后台破解/爬取"。
- **反面排除**：通用安卓自动化（无障碍 + 截屏 OCR，如 Open-AutoGLM-Hybrid）技术上存在，但**无证据表明阿尔法蛋在用**；逆向私有协议的说法在核验中被否掉。
- **置信度**：中。阿尔法蛋直接证据只有 #1 那一条；元萝卜是不同产品，属类比。要升到"事实"需对设备做**抓包/流量拆解**。

**这对我们意味着（关键）：野狐手机 App 只有两个版本，都免 Windows，但一个要合作、一个踩 ToS：**

| | 官方设备配对（阿尔法蛋/元萝卜真实路子） | App 自动化（我们能自助上的唯一替代） |
|---|---|---|
| 免 Windows | ✅（野狐 App 是安卓，RK3562 能跑） | ✅ |
| 天生 human-relay | ✅（就是"人人对弈"形态） | ✅ |
| 封号风险 | 低（设备级授权，合规） | **高**（操控账号，踩 ToS） |
| 我们能自助上吗 | ❌ **需野狐/腾讯商务合作**（私有白名单，无公开自助 SDK/API） | ✅ 但易随 App 改版碎、需反检测、维护量大 |
| 工程量 | 取决于合作后给什么（SDK/握手/配对协议） | **大**（落子→点击映射 + 对手落子 OCR + 反检测 + 长期维护） |

> **残酷结论**：阿尔法蛋那条"干净、免 Windows、天生适合人人对弈"的手机 App 路，**本质是商务合作**（野狐给白名单硬件的设备级授权），**没有自助技术版本**。想上手机 App 又不谈合作，就只剩 App 自动化——踩 ToS、封号风险高、只能做 Demo，不能出货。

## 7.6 决策岔路（野狐三条路的取舍）

| 路径 | 通道 | 免 Windows | 封号风险 | 前置条件 | 定性 |
|---|---|---|---|---|---|
| **A / B** | PC 客户端 `$FA/$AF` AI 认证口 | ❌ 需 Windows 跑野狐客户端 | 低（半官方 AI 认证） | 申请 AI 认证 | "AI 机器下棋"语义，human-relay 是否被接受需向野狐确认 |
| **C-官方** | 手机 App 设备配对 | ✅ | 低 | **野狐/腾讯商务合作**（用户此前对野狐划过"不走商务"的线，需重新确认） | 天生"人人对弈"，最干净，和阿尔法蛋同款 |
| **C-自动化** | 手机 App 无障碍/OCR | ✅ | **高** | 无 | ToS 违规，只配做 Demo/原型，不可出货 |

⚠️ **纠正一个易犯的误解**：Path B 的"自研 Controller 跑 Linux" **≠ 免 Windows**。`$FA/$AF` 那条 TCP 线的另一端**永远是野狐官方 Windows 客户端**（登录账号、真正在野狐服务器落子的 GUI）；我们能把 Controller 放 Linux，但**换不掉那个客户端**。想在 Linux/安卓上免掉它，只能走手机 App（Path C）——而 Path C 的干净版要合作。（调研提出"能否在 Linux 直接说 $FA/$AF 免 Windows"是 misframe：我们这一侧本就能在 Linux，被 Windows 锁死的是**客户端**那一侧。）

**推荐决策序：**
1. **先跑 §8 的 P0/P1（Path A PoC）** —— 无论最终选哪条，验证"human-relay 时间控制 + 野狐是否接受"都是最便宜的高价值实验，Path A 一台 Windows 即可。
2. **同时决策商务边界** —— 若可接受与野狐/腾讯谈合作，**Path C-官方是唯一干净、免 Windows、天生 human-relay 的路**（阿尔法蛋同款），应争取设备级合作；这与你早前"野狐不走商务"的判断冲突，需重新拍板。
3. **想把阿尔法蛋"官方 vs 自动化"从中等置信度升到事实** —— 对阿尔法蛋/元萝卜设备做一次**抓包/流量拆解**，确认它命中的是官方设备 API 还是驱动 App UI；这决定合作能拿到什么。
4. **App 自动化（C-自动化）只当一次性 Demo**，永不作为出货方案。

## 8. 分阶段落地建议

- **P0（阻塞项）**：申请 AI 认证；发邮件问野狐 —— human-relay 合规？账号是否限制排位/段位？慢棋时间控制建议？Windows 客户端能否无人值守长期运行？
- **P1**：Path A PoC —— Windows 跑 Fox 客户端 + FoxGTP（TCP 接 kiosk 后端 GTP 适配器），用一盘**慢棋**跑通 human-relay。复用现有 GTP 引擎接口。
- **P2**：闭环 —— 视觉识别落子 → `genmove` 返回；对手落子 → LED 引导。复用 physical-play 编排（`project_kiosk_golaxy_physical_play` / `project_kiosk_physical_play`）。
- **P3**：时间控制策略（自动接受对局邀请仅限长时限）+ 断线恢复 + 数子/中国规则。
- **P4（可选）**：Path B 自研 Controller，去 FoxGTP。
- **悬而未决（P0 决定生死）**：合规定性、账号排位限制、Windows 客户端托管方案（用户 PC vs 云 VM vs 随机出货）。
