升降级对弈：两套并行实现的取舍

origin/develop 上已有一套完整的升降级对弈实现（来自 codex/ai-ladder-ranked-module， 37 个提交里占 19 个），与本分支 S1–S4 相互独立地做了同一件事。两者共用同一个 game_type = 'ai_ladder_ranked'。本文逐条对照，供你决定以哪一套为准。

建议：以 develop 为准

保留 移植 3 项后删除

develop 那套在结算正确性上做得更深：待结算对局落库、对手配置冻结快照、 行锁与显式事务、结算时二次校验档位与认证状态、数据库层约束、旧账本迁移。这些都是难补的地基。 本分支独有的是三项契约与诚实性的收紧，落点明确、移植成本低： 引擎不可用时的账本守卫（develop 同样缺）、盘面条件服务端固定、逐局权威结算回执。

为什么不能两套并存

只有 10 个文件会产生文本冲突。真正的风险在干净合并的那部分—— 两套实现的文件名几乎完全不重叠，git 会把它们并排合进来，然后：

阻断
同一局棋会被结算两次
两条结算路径都挂在 game_type = 'ai_ladder_ranked' 上。 ladder_repo.settle_game 与 ai_ladder_ranked.settle_game 各自幂等， 但彼此之间没有任何互斥——一局棋会在两本账上各记一次，两套段位各走一步。
阻断
两套 schema 描述同一个概念
users 上的 5 个 ai_ladder_* 列 + ai_ladder_ledger， 与 ai_ladder_profiles + ai_ladder_pending_games + ai_ladder_game_ledger 同时建表。哪一张是段位的真相，代码里没有答案。
次生
两套 UI 抢同一个入口
kiosk 的 /kiosk/play/ai/setup/ranked 在本分支是独立的 LadderSetupPage，在 develop 是 AiSetupPage 的 isRanked 分支。 路由表里只能有一个赢。

数据模型

升降级规则本身两边一致：5 局定级赛、净胜 ±3 升降一档（存储值域 −2…2）、档位 1–41。差别全在持久化与并发。

各自独有能力

develop 独有

  • 待结算对局持久化——服务端重启 / 会话过期后仍能把已结束的对局结算掉
  • 冻结对手配置快照——结算时能证明当时打的是哪一档的哪一份配置（config_digest + execution_identity）
  • 数据库层约束——档位越界、定级局数越界在 DB 就被拒
  • 行锁 + 显式事务 + 乐观锁列
  • 结算时二次校验认证状态与对手档位是否匹配 profile 期望
  • 旧账本安全迁移、节点权威标志
  • 跨会话 ranked 分析封锁、重复认输冻结、trusted ranked 实体对局
  • 测试体量：test_ai_ladder_api 1 748 行 + test_ai_ladder_ranked 599 行

S1–S4 独有

  • 引擎不可用时的诚实状态 + 账本守卫——develop 同样缺这一条
  • 盘面/规则/贴目服务端固定在标定条件上，客户端无从更改
  • 逐局权威结算回执（settled + reason），不靠前后 diff 猜
  • RK3562 真机承重实测：最高状态 481 = 481 不溢出，开始按钮完整可见
  • 横向拖动不再退出 app（真机验证）
  • 10 个启用语种的 i18n 补齐
  • 测试体量：ladder_repo 224 + progress 189 + game_types 52 + stalled 133 行

各自现存缺陷

两边都有
引擎开不了局时，界面假装在思考，账本可能凭空发出升段额度
last_ladder_error 在两个分支上都没有任何前端消费者， 两边的 settle_game 也都没有引擎不可用的守卫。RK3562 上实测复现：AI 一手不下、 横幅停在「AI 思考中…」、对手时钟走完后 galaxy 自动判负 → 人类"获胜"入账。 本分支已修（d7fca9b3），develop 未修。
develop
9 路让 9 子赢一局，也会升段
/start 接受 board_size、rules、komi、 handicap，而 _ignored_reason 只校验 game_type / 胜负 / 认证 / 档位匹配， 从不看盘面条件。档名描述的是 19 路中国规则贴 7.5 下的棋力，别的条件下这个名字不成立。 当前 UI 在 ranked 分支隐藏了这些控件，但契约仍然敞着。
develop
结算反馈依赖 sessionStorage，丢了就说不清
换标签页、刷新、kiosk 重启都会丢掉 before， 此时只剩一句「当前状态已更新」；而「净胜没变」与「这局根本没计入」本就该是两句不同的话。
S1–S4
已结束但未结算的对局会随进程丢失
对手档位只存在内存 session 上，服务端重启即消失，没有 develop 的 pending_games 兜底。
S1–S4
结算时不复核对手档位与认证状态
只信开局时写进 session 的档位；没有 develop 的 opponent_rung_mismatch 这一层。也没有数据库约束与行锁。

迁移成本

方向 A · 以 develop 为准（建议）

删除 后端 ladder_repo.py · ladder_progress.py · ladder_catalog.py · /api/ladder/*（server.py 约 292 行）·users 上的 5 列与 ai_ladder_ledger； 前端 LadderSetupPage · LadderRankBand · LadderSettlementNote · LadderRankCard · LadderSettlementDialog · utils/ladderSetup.ts · utils/gameTypes.ts；对应 3 个测试文件
移植 1 引擎不可用守卫——在 ai_ladder_ranked._ignored_reason 增加 engine_unavailable 分支，前端在 features/aiLadder 里加诚实横幅 + galaxy 的 handleTimeout 短路。现成的实现与两条回归测试可直接改写。
移植 2 盘面条件收紧——把 board_size/rules/komi/handicap 从 AiLadderStartRequest 移除（或服务端强制覆盖），并在结算侧一并校验。
移植 3 逐局回执（可选）——develop 的 append-only 账本已经记下了每次结算尝试与忽略原因， 加一个按 game_id/会话反查的端点即可，比重做一套便宜。
冲突 10 个文件仍需手工合并，但规则简单：ladder 相关一律取 develop 侧， 本分支只保留 useGameSession 的 resign/timeout 修复等非 ladder 改动。

方向 B · 以本分支为准

代价 需要撤销 develop 上 19 个已合入主干的提交，并丢掉待结算持久化、配置冻结快照、 DB 约束、行锁、旧账本迁移与 2 300+ 行测试。
连带 主干上已有其他工作依赖 features/aiLadder（如 kiosk 账户页的段位展示 80cbaab7）， 撤销会一并断掉。
结论 成本高于方向 A，且与主干协作方向相反。除非你认为 develop 那套的结算语义有根本问题—— 我没有发现这样的问题。
