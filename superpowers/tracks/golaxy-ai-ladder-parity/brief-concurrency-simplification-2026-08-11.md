## 0. 一句话

**并发只靠一把占位锁。「另一台设备是不是真的死了」这个问题，不要回答。**

我们四家之前都在往同一个方向修：加心跳、加失联判定、加接管窗口、加放弃窗口。
产品方叫停了，理由一句话就说完：

> 这不是两个用户在争抢，是**同一个人站在两台机器之间**。他就在屏幕前，直接问他即可。

所以：**开新局 = 立即夺占位。没有门槛、没有窗口、没有倒计时。**

## 1. 删掉什么（对照你自己的实现）

围棋这边删掉的东西，按概念列，你们的命名会不一样：

| 删 | 它在回答什么 |
|---|---|
| 接管门槛常量 + 其 version | 另一台设备失联多久算死 |
| 放弃结算门槛常量 + 其 version | 成绩送不出去等多久算放弃 |
| `takeover_eligibility()` | 现在能不能接管 |
| `abandoned_settlement_eligibility()` | 现在能不能放弃等待 |
| 认输闸的三态（拒绝 / 窗口内 / 放行） | 同上，投影层再算一遍 |
| 两个「时机不对」异常 | 同上 |
| 阻塞局投影里的 8 个字段 | 把上面这些算出来的结果发给前端 |

围棋实测：**后端净 −931 行**，测试删掉 11 条（它们全都是为已删规则写的）。
**两条产品保证一条没丢**——见 §2。

### ⚠️ 删之前先确认这一条（我一开始判断错了，差点保留错的东西）

我原以为「防止用户靠断线躲掉一场负」靠的是**记那场负**。查完代码发现不是：

- 真正的威慑是**占位锁本身**（一个账号最多一行 active）。
- 没有任何后台任务会自动结算被遗弃的局——`_cleanup_locked()` 只关引擎。
- 所以那一局会**永远挡着这个账号打排位**，直到有人付出代价把占位拿回来。

⇒ **记下的那场负不是惩罚，是「把占位赎回来」的价钱。**
既然如此，那一整套「他是不是真死了」的推断就全是多余的：他想开新局，就付价钱；
不想付，那一局就一直挡着。两种结果都自洽，都不需要系统去猜。

**请各自确认你们的实现里也是这个结构**（占位锁是唯一约束、没有自动清扫器）。
如果你们有自动清扫器，那结论不一样，先告诉我。

## 2. 两条产品保证（不许丢）

1. **一个账号不得同时进行两局排位。** ← 占位锁
2. **不得靠断线躲掉一场负。** ← 夺占位时按状态记账

第 2 条的记账规则，**由服务端按那一行的状态决定，不由前端挑**：

| 被顶掉的那一局 | 记什么 |
|---|---|
| 还在下（active） | **记一场负**，计入升降级 |
| 已下完、成绩还在送（pending_settlement） | **什么都不记**；成绩送到了仍按真实结果算 |

第二行成立的前提：**账本按 game_id 先到先得**。晚到的那份结算照样入账，且不会打扰
新开的那一局。请确认你们的结算也是按 game_id 幂等的——不是的话这条规则不成立。

## 3. UI 收敛成两格、一个按钮

```
A) 那局还在别处 / 接不回来
   文案：这一局正在你的另一台设备上进行。
   按钮：[在这台机器上开新局]
   按钮下一行：那一局会记为本局负，并计入升降级

B) 上一局成绩还在送
   文案：这一局已经下完，成绩还没送到云端。
   同步行：重试 2/5 · 4:12 后自动重试        ← §4
   按钮：[立即重试]  [在这台机器上开新局]
   按钮下一行：那一局不计入本次开局；成绩送到了仍按它真实的结果计算
```

三条硬要求：

1. **代价写在按钮下面，不写在二次确认里。** 写在弹窗里等于按下之后才说。
2. **代价每次现算，包括弹窗开着的时候。** 同一局从「在下」变成「成绩未送达」，
   那句话必须当场从「记为负」改成「什么都不记」——否则用户照着一句已经不成立的话按下去。
3. **删掉「刷新状态」。** 它做的事（重问一次状态）挡局面板本来就在定时自动做，
   所以它在每一格要么是别的按钮的真子集，要么什么都改不了。
   **例外**：老服务端只回一个 pending 标志、不回阻塞局对象的兼容分支——那一格
   没有自动轮询，手动问一次是唯一能推进事情的办法，留着。

## 4. 「立即重试」的契约（有 outbox 的才需要）

如果你们的成绩是经**本机出站队列**送到云端的，这一节适用；如果是同步直发，跳过。

### 4.1 屏上要说的话，全部来自队列，一个都不许前端推

```json
{
  "state": "sending | waiting | exhausted | refused | synced",
  "attempt": 2, "max_attempts": 5,
  "next_attempt_in_seconds": 252,
  "last_http_status": null, "last_error": null,
  "receipt": { "counted": true, "reason": null }   // 只在 synced 时有
}
```

**`next_attempt_in_seconds` 必须是时长，不是时刻。** 常年离线、没有可靠 NTP 的一体机
正是钟偏最大的那台；用时刻算倒计时，差多少钟就错多少。

**`exhausted`（网络坏了一阵）和 `refused`（云端在事实上拒收）必须分开。**
只有前者值得再按一次。422 问一百遍还是 422，给一个按不出结果的按钮比不给更坏。

### 4.2 四个坑（都是围棋这边实测踩到的）

**① 离线时点「立即重试」会毁掉面板 —— 最严重的一个**

这个按钮存在的理由就是网络不好。而如果失败之后你去**刷新一次状态**来更新屏幕，
而那个状态接口是转发到云端的，它会在同一个断网下失败，把整块面板换成「加载失败」。

⇒ **失败路径一步都不许碰云端。** 重试请求本身打的是本机（127.0.0.1），断网照样成功，
它的响应里就带着这一次尝试之后的真实状态——那是此刻手上**唯一确定收到过**的事实，用它。
**只有送成了才去刷新**：那一刻网络刚被证明是通的。

**② 成功之后什么都不说**

送成之后面板悄悄消失、段位数字自己变了，用户不知道这一局到底计没计。
⇒ 队列在成功响应里本来就拿到了云端的裁决（计没计、为什么），**收下来发到屏上**，
复用你们已有的结算回执 UI。拿不到就只刷新，**不许编一个结果出来**。

**③ 会话过期时屏上说「正在送」**

队列在 auth 失效时通常整个暂停。此时按下去一步都不会走，而屏上会显示「正在送」。
⇒ 端点先检查这个标志，直接 401，走「登录已失效，请重新登录」那条既有文案。

**④ 倒计时走完不要说「正在重试」**

队列多半是**定时排空**的（围棋这边 60 秒一轮）。到期只保证「下一轮会带上它」，
不保证此刻正在发。⇒ 走完改说「**即将重试**」。也不许停在一个 0:00——那是这块屏
唯一会被当成卡死的画面。

### 4.3 完整分支表（照着自测）

| 按下之后 | 屏上 | 打云端吗 |
|---|---|---|
| 送成 | 结算已完成 + 计入/不计入及原因 | 刷新 |
| 送成但拿不到回执 | 面板消失、段位更新 | 刷新 |
| 5xx / 网络断 | 重试 3/5 · 1:20 后自动重试 | **不** |
| 重试用尽后再按 | 预算归零重来，失败回到 1/5 | **不** |
| 4xx 拒收 | 拒收文案，重试按钮消失，代价改成「不计入」 | **不** |
| 正在送 | 正在把成绩送到云端…（不重复触发） | **不** |
| 会话过期 | 登录已失效，请重新登录后再试 | **不** |
| 队列里已没有这一局 | 面板消失 | 刷新（唯一去刷新的 catch） |
| 本地接口 500 | 重试失败，请稍后再试（面板保持） | **不** |
| 连点两下 | 前后端各一道锁 | — |
| 无 outbox（网页直连） | 按钮根本不出现 | — |

## 5. 不要照抄围棋的部分

- **具体文案**：我们的对手叫「智星棋手」、单位是「段」。你们各自换。
- **`+F` vs `+R`**：围棋把远端结束写的棋谱结果从「认输」改成「弃权」，因为云端手上
  一手棋都没有，写认输等于声称这是一盘下过、并在某一手停下的棋。**这条精神通用，
  记法各棋种自己定。**
- **60 秒排空周期**：看你们自己的连通性管理器。
