## 0. 一句话

**并发只靠一把占位锁。「另一台设备是不是真的死了」这个问题，不要回答。**

我们四家之前都在往同一个方向修：加心跳、加失联判定、加接管窗口、加放弃窗口。
产品方叫停了，理由一句话就说完：

> 这不是两个用户在争抢，是**同一个人站在两台机器之间**。他就在屏幕前，直接问他即可。

所以：**开新局 = 立即夺占位。没有门槛、没有窗口、没有倒计时。**

## 1. 删掉什么（对照你自己的实现）

围棋这边删掉的东西，按概念列，你们的命名会不一样：

| 删 | 它在回答什么 |
|---|---|
| 接管门槛常量 + 其 version | 另一台设备失联多久算死 |
| 放弃结算门槛常量 + 其 version | 成绩送不出去等多久算放弃 |
| `takeover_eligibility()` | 现在能不能接管 |
| `abandoned_settlement_eligibility()` | 现在能不能放弃等待 |
| 认输闸的三态（拒绝 / 窗口内 / 放行） | 同上，投影层再算一遍 |
| 两个「时机不对」异常 | 同上 |
| 阻塞局投影里的 8 个字段 | 把上面这些算出来的结果发给前端 |

围棋实测：**后端净 −931 行**，测试删掉 11 条（它们全都是为已删规则写的）。
**两条产品保证一条没丢**——见 §2。

### ⚠️ 删之前先确认这一条（我一开始判断错了，差点保留错的东西）

我原以为「防止用户靠断线躲掉一场负」靠的是**记那场负**。查完代码发现不是：

- 真正的威慑是**占位锁本身**（一个账号最多一行 active）。
- 没有任何后台任务会自动结算被遗弃的局——`_cleanup_locked()` 只关引擎。
- 所以那一局会**永远挡着这个账号打排位**，直到有人付出代价把占位拿回来。

⇒ **记下的那场负不是惩罚，是「把占位赎回来」的价钱。**
既然如此，那一整套「他是不是真死了」的推断就全是多余的：他想开新局，就付价钱；
不想付，那一局就一直挡着。两种结果都自洽，都不需要系统去猜。

**请各自确认你们的实现里也是这个结构**（占位锁是唯一约束、没有自动清扫器）。
如果你们有自动清扫器，那结论不一样，先告诉我。

## 2. 两条产品保证（不许丢）

1. **一个账号不得同时进行两局排位。** ← 占位锁
2. **不得靠断线躲掉一场负。** ← 夺占位时按状态记账

第 2 条的记账规则，**由服务端按那一行的状态决定，不由前端挑**：

| 被顶掉的那一局 | 记什么 |
|---|---|
| 还在下（active） | **记一场负**，计入升降级 |
| 已下完、成绩还在送（pending_settlement） | **什么都不记**；成绩送到了仍按真实结果算 |

第二行成立的前提：**账本按 game_id 先到先得**。晚到的那份结算照样入账，且不会打扰
新开的那一局。请确认你们的结算也是按 game_id 幂等的——不是的话这条规则不成立。

### 🔴 2026-08-11 更正：上面那张表的第二行，**围棋自己也不成立**

五子棋 track 报回「`terminal_pending` 从来没人写」，象棋 track 报回「云端分不出
『还在下』和『下完了、成绩在送』」。我原本回复两家说围棋这一格是通的。**我去验了，
我说错了。围棋病得更隐蔽。**

围棋**写了**那个通知（`remote_client.mark_ai_ladder_game_pending`，盒子在本地结算成功后
调一次）。所以 grep 得到调用点，看起来这一格是通的。但它在 `try/except` 里，
**失败只记一条 warning 就吞掉**，而且：

- 全仓**只有这一个调用点**，没有任何补偿；
- outbox 只有 `settle_ai_ladder_ranked` **一种** operation，那条通知不入队、不重试；
- 盒子上 `ai_ladder_repo` 是**本机**库，错误分支里再标一次 pending 改的是本地行，云端不受影响。

**而它失败的场景，就是断网——正是 outbox 存在的全部理由。通知和结算走同一条网络，
所以这一格恰好在它唯一被需要的时候失效。**

实测链条（围棋，断网结束一局，用户**赢了**）：

1. 本地结算成功，账本记「胜」
2. `mark_ai_ladder_game_pending` → 断网 → warning，吞掉
3. 结算进 outbox
4. **云端那一行仍是 `active`**
5. 换台机器点「在这台机器上开新局」→ `POST /games/{id}/end` 读到 `active`
   ⇒ `finalize_reserved_game(terminal_source="remote_resign", result="loss")` ⇒ **记一场负**
6. 网络恢复，真结算送到 → 命中已有账本行 → **原样返回那份判负回执**

净效果与五子棋报的一字不差：**他赢的那局变成一场负，全程无报错。**

⇒ **这不是某一家的实现疏漏，是四家共有的结构问题。** 根子在一句话：
**「本地已下完、成绩还在送」这个事实存放在那台断网的盒子上，云端在它连不上的时候
无从知道**。写得再勤也没用——通知本身也要过网。

**这一格现在是四家共同的未决项，等产品方（Fan）拍板，谁都先别按第二行落地。**
三个候选（象棋提了前两个，第三个是围棋验完之后补的）：

| | 做法 | 代价 |
|---|---|---|
| (a) | 一律记负，晚到的真结算按幂等丢弃 | 用户赢的局变成负，**违背保证 2 的本意** |
| (b) | 夺占位时由发起端自报「那局我下完了」 | 自报即可免罚，**保证 2 形同虚设** |
| (c) | **记一个「暂记」的负，真结算到达时覆盖它** | 需要账本允许一次特定覆写 |

**围棋 track 倾向 (c)**，理由：这与已经写进 §1 的那句话是同一个道理——
**「记下的那场负不是惩罚，是把占位赎回来的价钱」；价钱在真收据到达时应当可退。**
(c) 不重新引入任何「他是不是真死了」的推断，只多一个判别位：账本行已经有
`terminal_source`，`remote_resign`（猜的）和 `played_result`（真的）本来就分得开，
覆写条件就是「猜的被真的取代」，且只允许这一个方向。保证 2 仍然成立——暂记的负
当场就落，躲不掉；而真结算带的是盒子测到的真实结果，盒子在这套设计里本来就是
played_result 的权威，不构成新的信任让步。

#### ⚠️ (c) 的真实成本不在判别位上，在「拿什么退」（五子棋 track 提出，围棋已量）

我们讨论了半天「怎么认出该退」，**没人量过「退得动吗」**。五子棋报回：Glicko-2 三元组
路径依赖，回执里一个评分内部量都没有，退款要么另存一份结算前快照，要么把整条评分史重放。

**围棋量完，同病。** 结算把 profile 六元组
（`ai_ladder_rung / placement_lo / placement_hi / placement_completed / net_score / version`）
就地改掉，而**账本行、pending 行、回执，没有任何一处留下结算前的值**——`_lifecycle_receipt`
读的是**改完之后**的 profile。

而且**转移不可逆**，有具体二义性（不是「大概难」）：

```python
net_score += -1              # 输一局
if net_score <= -3: rung = step(rung, -1); net_score = 0
```
> 已知「输了一局」和结算后的 `net_score == 0`，前态有**两个**：
> ① `net_score = 1`，没触发降级；② `net_score = -2`，触发了降级、掉了一级。
> 两者结算后都是 0。**光看后态分不出该不该把那一级还回去。**
>
> 定级期更糟：`placement_hi = (lo+hi)//2` 是整除，前态 `hi` 有两个候选。

⇒ **围棋 (c) 也要加一份结算前快照。** 判别位是现成的（而且是独立列，不在 JSON 里，
比五子棋方便一点），但退款依据是零。

**⇒ 请各家在报 (c) 成本时，把这两件事分开报**：
①「能不能认出该退」（判别位）②「拿什么退」（结算前快照）。
只报 ① 会**系统性低估** (c) 的成本——四家目前全都低估了。

**还有一格归产品**（五子棋提出）：那笔暂记的负已经消耗了一个结算序号 / 占了一行账。
覆写时这个号是**留着**（那这个号对应的事实变了）还是**再消耗一个**（那用户账面上多一笔）？
这是语义，不是实现细节。

⇒ 我原话「(c) 的代价是账本需允许一次特定覆写」，**在象棋要重写成「账本需要放弃它现在

#### 🔴 更硬的一条：**「退」不等于「恢复到快照」**（象棋 track 提出，四家通用）

被顶掉之后账号**立刻**可以开新局，而那一局可能**先于**晚到的结算落库。此时账号的评分/段位
已经因为**中间那一局**动过了。把档案设回结算前快照，会把**中间那一局一起抹掉**。

⇒ **(c) 必须是补偿式的（记一笔反向变动），不能是回滚式的。** 而「有快照」只解决回滚式。
象棋因此指出：拆掉「不许 UPDATE」得到的是回滚式，**而回滚式是错的**——那条不变量拆了也不够。

**围棋对这一问的答案（已量）**：围棋能靠**重放**正确处理，因为记账权威（云端）那一侧
profile 的写入点只有两个——创建（`initial_placement_window(user.rank)`，确定性种子）和
`_apply_result`，而 `_apply_result` 是 (profile, result) 的**纯函数**：无墙钟、无衰减、无随机。
⇒ 把账本按序重放一遍，中间那一局自然落在正确位置，**不需要快照，也不会抹掉它**。

两条围棋自己的附注，不许当成已解决：
- 盒子那一侧有 `adopt_remote_profile`（整体覆盖云端答案、`version+1`、**不留痕**，唯一调用者
  `sync_worker.py:204`）。它不破坏云端的可重放性——盒子那份是显示镜像，不是记账权威——
  但**「盒子上的段位不可重放」这件事本身要记着**。
- 重放需要**顺序**，而晚到的结果该按「对局结束时刻」还是「到达时刻」入列，**是个决定**：
  `_apply_result` 是顺序相关的（净胜分累积、阈值触发），两种放法结果不同。账本有 `decided_at`
  可用，但用哪个是产品语义。

## 3. UI 收敛成两格、一个按钮

```
A) 那局还在别处 / 接不回来
   文案：这一局正在你的另一台设备上进行。
   按钮：[在这台机器上开新局]
   按钮下一行：那一局会记为本局负，并计入升降级

B) 上一局成绩还在送
   文案：这一局已经下完，成绩还没送到云端。
   同步行：重试 2/5 · 4:12 后自动重试        ← §4
   按钮：[立即重试]  [在这台机器上开新局]
   按钮下一行：那一局不计入本次开局；成绩送到了仍按它真实的结果计算
```

三条硬要求：

1. **代价写在按钮下面，不写在二次确认里。** 写在弹窗里等于按下之后才说。
2. **代价每次现算，包括弹窗开着的时候。** 同一局从「在下」变成「成绩未送达」，
   那句话必须当场从「记为负」改成「什么都不记」——否则用户照着一句已经不成立的话按下去。
3. **删掉「刷新状态」。** 它做的事（重问一次状态）挡局面板本来就在定时自动做，
   所以它在每一格要么是别的按钮的真子集，要么什么都改不了。
   **例外**：老服务端只回一个 pending 标志、不回阻塞局对象的兼容分支——那一格
   没有自动轮询，手动问一次是唯一能推进事情的办法，留着。

## 4. 「立即重试」的契约（有 outbox 的才需要）

如果你们的成绩是经**本机出站队列**送到云端的，这一节适用；如果是同步直发，跳过。

### 4.1 屏上要说的话，全部来自队列，一个都不许前端推

```json
{
  "state": "sending | waiting | exhausted | refused | synced",
  "attempt": 2, "max_attempts": 5,
  "next_attempt_in_seconds": 252,
  "last_http_status": null, "last_error": null,
  "receipt": { "counted": true, "reason": null }   // 只在 synced 时有
}
```

**`next_attempt_in_seconds` 必须是时长，不是时刻。** 常年离线、没有可靠 NTP 的一体机
正是钟偏最大的那台；用时刻算倒计时，差多少钟就错多少。

**`exhausted`（网络坏了一阵）和 `refused`（云端在事实上拒收）必须分开。**
只有前者值得再按一次。422 问一百遍还是 422，给一个按不出结果的按钮比不给更坏。

### 4.2 四个坑（都是围棋这边实测踩到的）

**① 离线时点「立即重试」会毁掉面板 —— 最严重的一个**

这个按钮存在的理由就是网络不好。而如果失败之后你去**刷新一次状态**来更新屏幕，
而那个状态接口是转发到云端的，它会在同一个断网下失败，把整块面板换成「加载失败」。

⇒ **失败路径一步都不许碰云端。** 重试请求本身打的是本机（127.0.0.1），断网照样成功，
它的响应里就带着这一次尝试之后的真实状态——那是此刻手上**唯一确定收到过**的事实，用它。
**只有送成了才去刷新**：那一刻网络刚被证明是通的。

**② 成功之后什么都不说**

送成之后面板悄悄消失、段位数字自己变了，用户不知道这一局到底计没计。
⇒ 队列在成功响应里本来就拿到了云端的裁决（计没计、为什么），**收下来发到屏上**，
复用你们已有的结算回执 UI。拿不到就只刷新，**不许编一个结果出来**。

**③ 会话过期时屏上说「正在送」**

队列在 auth 失效时通常整个暂停。此时按下去一步都不会走，而屏上会显示「正在送」。
⇒ 端点先检查这个标志，直接 401，走「登录已失效，请重新登录」那条既有文案。

**④ 倒计时走完不要说「正在重试」**

队列多半是**定时排空**的（围棋这边 60 秒一轮）。到期只保证「下一轮会带上它」，
不保证此刻正在发。⇒ 走完改说「**即将重试**」。也不许停在一个 0:00——那是这块屏
唯一会被当成卡死的画面。

### 4.3 完整分支表（照着自测）

| 按下之后 | 屏上 | 打云端吗 |
|---|---|---|
| 送成 | 结算已完成 + 计入/不计入及原因 | 刷新 |
| 送成但拿不到回执 | 面板消失、段位更新 | 刷新 |
| 5xx / 网络断 | 重试 3/5 · 1:20 后自动重试 | **不** |
| 重试用尽后再按 | 预算归零重来，失败回到 1/5 | **不** |
| 4xx 拒收 | 拒收文案，重试按钮消失，代价改成「不计入」 | **不** |
| 正在送 | 正在把成绩送到云端…（不重复触发） | **不** |
| 会话过期 | 登录已失效，请重新登录后再试 | **不** |
| 队列里已没有这一局 | 面板消失 | 刷新（唯一去刷新的 catch） |
| 本地接口 500 | 重试失败，请稍后再试（面板保持） | **不** |

## 6. 请回我这几件事

1. 你们的实现里，占位锁是不是唯一约束？**有没有自动清扫器？**（§1 结尾）
2. 结算是不是按 game_id 幂等、先到先得？（§2）

### 4. 「已下完、成绩在送」这一档，**真的有人写它吗？**（五子棋 track 提出，围棋验完后升为四家必查）

> 契约声明的每个状态，都得有人写它。

判据不是「grep 得到这个状态名」——围棋 grep 得到、而且确实写了，仍然是坏的。**要问的是：
在那条通知失败的场景下，还有谁会把它写上去？** 围棋的答案是「没有人」，于是它在最需要的
时候（断网）永远不生效。

三步自查：

1. 那一档由**哪一次写入**产生？找到那行代码。
2. 那次写入**过网吗**？过网的话，它和结算是不是同一条网络？
3. 它失败了谁补？**入队重试了吗，还是 `except: log`？**
4. **判错了拿什么改回来？**（五子棋 track 补的第 4 步）判别位只解决「认出该退」，
   不解决「退得动」。评分类系统尤其：Glicko-2 / Elo / 净胜分升降级**都是路径依赖的**，
   **没有结算前快照就没有退款**，而这件事在「加个判别位」的讨论里天然隐身。

四步走完只要有一步答不上来，§2 第二行在你们那儿就是**反向生效**：用户赢下的局记成一场负，
且后到的真结算会被幂等逻辑正确地丢弃。**症状是段位莫名下降，没有任何报错。**

**查这一格时的方法注意**（象棋 track 的教训，值得四家都收）：他们第一次用 ORM 改字段探针，
拿到 `overwrite=OK`，**差点报成「象棋账本可以覆写」**——真相是那次赋值把 `result` 从
`'win'` 改成 `'win'`，**SQLAlchemy 压根没发 UPDATE**。补了正对照（先列出库里真有哪些触发器 →
用裸 SQL 发一条真 UPDATE → 读回来比值）才拿到正确结论。

> **「操作成功」和「操作发生过」是两件事。**「没被拒绝」和「没发生过」长得一模一样。
> 探针拿到绿，先问这个绿有没有区分度。

这和我们前几天那条「投影里声明的每个取值都得有人产生」是同一个病，只是载体从投影字段
换成了数据库状态机。

### 5. 占位锁的谓词，和结算入口的前置条件，**是同一个表达式吗？**（象棋 track 提出）

象棋两处都是 `status == 'reserved'`：占位锁靠它，`_settle_in_session` 也要求它。
⇒ **「把 status 挪出 reserved 来释放占位」会顺手把晚到的结算一起拒掉**，而那正是
§2 第二行要保住的东西。是同一个表达式的话，「释放占位」这个动作没法只改那一个位。

象棋的解法（推荐给同构的实现）：加一列 `superseded_at`，谓词改成
`status='reserved' AND superseded_at IS NULL`。不新增状态值、不动既有 CHECK、不删任何行，
外键和晚到结算的落地路径全部原样成立。

**顺带**：账本行是否有外键指向预约行？有的话（象棋有，围棋没有）**不能删那一行**，
只能改状态位。删法各家按自己的 schema 定，别照抄围棋。

#### ⚠️ 这条在国象是**另一个形态，而且简化模型会把它引爆**（国象 track 实测）

国象两个谓词共用同一行，但结算入口是「**账本行在 _或_ 预约行在**」——所以**账本墓碑**
是解耦的关键。带阳性对照实测：

```
有账本墓碑 + 删预约 → 晚到的真结算 200，拿回执     ← 阳性对照
无账本墓碑 + 删预约 → 晚到的真结算 404
```

盒端把 404 归 `SettlementPermanent` ⇒ 本地标 conflict ⇒ **那一局真实的结果被永久丢弃**。

**今天安全**，因为 force-resign 一定写账本。**但简化模型的 (b)「自报免罚」和围棋式的
「放弃等待」都会删预约而不写账本**——那一刻这条就变成活的。

国象已把它钉成不变式测试（`bb339d85`）：**释放占位的每一条路径都必须留墓碑**。
真加那种路径时它会红在**加它的那一刻**，而不是等某个用户的胜局莫名变成一场负。
变异测试（404 换 410，等价于解耦）→ 2 红，说明这个测试有区分度。

⇒ **四家自查**：你们「释放占位」的路径，有没有在账本里留下任何痕迹？没有的话，
晚到的真结算会不会被当成「这局不存在」而永久丢弃？

### 6. 幂等的两种情形分开了吗？（象棋 track 提出）

同一个 game_id **同一份载荷**再来一次 ⇒ 重放既有回执；
同一个 game_id **不同载荷** ⇒ 应当是 409，**不是静默丢弃**。后者是数据完整性事故，
不该长得像成功。
