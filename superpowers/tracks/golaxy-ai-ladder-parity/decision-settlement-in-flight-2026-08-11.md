# 请拍板：「成绩还在送」的那一局，被顶掉时记什么

> 2026-08-11 · 四条 track 实测汇总 · 三家已停工等这个决定
> 技术细节见 `brief-concurrency-simplification-2026-08-11.md`，这一页只谈决定。

---

## 一句话

**用户在 A 机下完一局（比如赢了），成绩卡在断网盒子的出站队列里。他走到 B 机开新局，
夺占位。云端此刻只看得到「那一局是 active」——于是记他一场负。网络恢复后真结算送到，
幂等逻辑正确地把它丢弃。**

**净效果：他赢的那局变成一场负，全程无报错。症状是段位莫名下降。**

## 如果只读一句

国象把代价量出来了（Glicko-2，扫 75 组对手/结果组合，带阴性对照）：

> **一位用户赢了那一局，却因为跨机器开局被记成负。
> (a) 让他掉 34 分；(c) 把这 34 分还给他，代价是一列字段 + 一条端点 + 一次中继契约变更。**

34 分是国象产品等级档位的量级——**用户看得见**。（对照：下面待定项 2 的两种顺序规则，
在国象只差 0.3 分，中位数 0.301、最大 1.128，**不是同一量级的取舍**。）

## 为什么这不是某家写漏了

「本地已下完」这个事实**存放在那台断网的盒子上**。云端连不上它，就无从知道——
**通知本身也要过网**。

四家实测形态不同，病一样：

| | 形态 |
|---|---|
| 围棋 | 写了通知，但在 `try/except` 里，断网必然失败、只记一行 warning，不入队不重试 |
| 国象 | **这个机制根本不存在**，现场完全静默（连 warning 都没有） |
| 象棋 | 云端手上「已建局且没有账本行」和「还在下」长得一模一样 |
| 五子棋 | 盒端终局只打 `settle` 一个接口，从不通知 |

围棋那一格**最危险**：它看起来是通的，我自己就因此判断错了一次，还把错的结论转给了另外三家。

## 三个选项

### (a) 一律记负，晚到的真结算丢弃

即**当前行为**，零改动。
代价：**用户赢下的局变成一场负**，无报错。
若选这条，我会把「云端看不到那局的结果，你若已下完可能被记为负」写进夺占位前的提示——
不修，但不骗人。

### (b) 由发起端自报「那局我下完了」

改动最小，且与我们已定的简化精神同源（「他就在屏幕前，直接问他」）。
代价：**自报即可免罚**，「不得靠断线躲掉一场负」这条保证形同虚设。

### (c) 记一个「暂记」的负，真结算到达时更正它  ← 我建议这条

与已定的那句话同源：**「记下的那场负不是惩罚，是把占位赎回来的价钱」——价钱在真收据
到达时应当可退。** 两条产品保证都保住：暂记的负当场就落（躲不掉），真结果到了按真实结果算。
不重新引入任何「他是不是真死了」的推断。

**但 (c) 有一条今晚才发现的硬要求**（象棋提出，四家通用）：

> 被顶掉后账号**立刻**能开新局，那一局可能**先于**晚到的结算落库。
> **把段位设回结算前的快照，会把中间那一局一起抹掉。**
> ⇒ **(c) 必须是「补偿式」（从快照往前重算），不能是「回滚式」（设回快照）。**

## (c) 的四家代价（实测，不是估的）

| | 判别位<br>「认得出该退」 | 重算依据<br>「退得动」 | 写得回去 | 净成本 |
|---|---|---|---|---|
| **围棋** | ✅ 独立列现成 | ✅ **不需要快照**：云端记账只有一个写入点且是纯函数，按账本重放即可 | ⚠️ 没人拦，**但不等于可以** | 无 schema 改动<br>⚠️**代价是那条 append-only 静默失效**——见下 |
| **象棋** | ✅ 现成 | ✅ **已有快照**，且结算不现算（分数冻在账本行上），重放现成 | ❌ **数据库触发器拦死** | **一处 schema 改动，后面无连锁** |
| **国象** | ✅ 现成（建议新加显式位） | ✅ **实测逐位相同**，且输入**就在一行账本里**（不需链式重放） | ⚠️ 有一道版本闸挡着 | 一列 + 一条端点 + 一次中继契约变更 |
| **五子棋** | ⚠️ 埋在 JSON，建议提列 | ❌ **输入复现不了**：闲置衰减在开局路径改评分且不留痕，衰减了几个周期事后推不出来 | ✅ | 快照 + 评分事件日志<br>❓**此估算以「日志补齐后重放能对齐」为前提** |

### 重放保真度：一度是能让 (c) 直接不成立的未验项，现已查清

国象最先把这一格标为**未验**并指出：**如果重放对不齐，(c) 就不是「贵一点」，是不成立。**
随后他们把它量了（生产 `rate()` 不改、逐字节比而非 `==`、带阴性对照：第一局对手分扰动
`1e-9` 确实分开，证明比较有区分度）。结果：

**三个 ✅ 不是同一种 ✅**（象棋主动要求给自己降档，我把同一把尺子也量到了围棋头上）。
证据强度分三档，横排在一列里会被读成同一件事：

| | 重放保真度 | 证据档次 |
|---|---|---|
| **国象** | ✅ 逐位相同，输入就在一行账本里 | **实测，且覆盖「算 → 存 → 读 → 发」整条链**——真起云端结算一局，profile 列 / 账本列 / 线上回执 JSON 三处回读全部逐位相同；带阴性对照 |
| **围棋** | ✅ `_apply_result` 全整数（净胜分 ±1、阈值比较、档位步进），两个档位函数也已逐个验过：纯整数、无时钟无随机 | **源码层，肯定性论证**——「整数运算是精确的」是可判定的性质，但**没跑过重放** |
| **象棋** | ✅ 不现算，delta 冻在账本行上 | **源码层，否定性论证**——「没找到不确定性来源」。⚠️**没找到 ≠ 不存在** |
| **五子棋** | ❌ **不是浮点问题，是信息缺失**——衰减在开局路径改评分且不入账，**连输入都复现不了** | — |

**五子棋那一格性质不同，不该和浮点风险并列**（国象指出）：另外三家是「算得准不准」，
五子棋是「**算不算得出来**」。

**⇒ 若选 (c)，解冻后第一批该做的是取证而不是改代码**：围棋和象棋各补一次真跑
（冻结快照喂进生产算分、逐字节比、阴性对照），把两个源码层的 ✅ 抬到国象那一档。
不改代码，只补证据。**范围要覆盖「算 → 存 → 读 → 发」整条链**——国象一开始只测了算法内核，
自查后才补上库与线上往返；「实测」两个字不写清范围，下一个人会以为它覆盖了他关心的那一跳。

**而且取证方式要按各家的风险形状定，不是「都跑一遍」**（国象提出）：

| | 风险形状 | 取证方式 |
|---|---|---|
| 国象 | 平滑、小但常在（0.3 分） | 随机取样就能看见 |
| **围棋** | **量子化：多数时候差 0，跨阈值时差一整档** | **随机取样跑一万次也撞不到**——必须**专门构造净胜分恰好卡在阈值上**的用例 |

围棋那种形状不只更难取证，也**更容易在线上被当成偶发 bug**——因为它绝大多数时候完全正常。

**⚠️ 但有一个前提对四家同时成立**：重放是**顺序相关**的，而晚到的结果按哪个时刻入列
**还没定**（就是下面待定项 2）。所以四家的 ✅ 都是「**给定顺序规则之后**逐位可复现」，
不是「成本已经确定」。象棋的措辞值得抄：**「一处改动」，不是「一处改动且已确定」。**

### 国象还有两条要单独说

- **(a) 其实已经是国象今天的行为**——但不是设计出来的，是一道版本闸的副作用
  （晚到的结算跨过中间那一局会拿到 409）。而且**发生率高**：国象盒端从不告诉云端
  「本地已下完」，所以这不是「偶尔断网时」，是**每一次跨机器开局都可能**。
- **(b) 国象不能选，理由比「防作弊形同虚设」硬**：不写账本的释放会删预约，而国象结算入口是
  「账本行在**或**预约行在」⇒ 实测 404 ⇒ **(b) 想保住的那个结果，恰恰被 (b) 自己的实现方式丢掉。**

### ⚠️ 围棋那个 ⚠️ 要说清楚

围棋账本 `game_id` 也是唯一的，docstring 也写着 `Append-only`——**但没有任何触发器执行它**。

**围棋和象棋是同一个设计。区别只在象棋把不变量执行了，围棋只写在注释里。**

象棋 track 把这句话的分量又收紧了一格，我认为是对的：

> 不是「象棋卡在更前面一步」，是**四家卡在同一步，只有象棋会当场报错**。
> 那不是象棋更严，是**象棋会说话**。

⇒ **所以「围棋不用改 schema」这句话是误导性的省钱。** 若选 (c) 而围棋按现状直接写第二行，
那条 append-only 会在**没有任何红**的情况下失效——注释还在，不变量已经没了，
而且没有任何测试会因此变红来提醒下一个人。

**「没被拦住」不是「可以做」。** 围棋要么正式放弃那句 docstring（并删掉它），要么跟象棋
一样改主键。**这个选择我不替你做，但它必须是被选的，不能以「围棋反正没拦」的方式默默发生。**

象棋补的第三条路才是真正要防的：

> 要么改主键，要么正式放弃并**删掉**那句 docstring。
> **留着骗人是第三条路，而它是今天的默认路径。**

⇒ 这一格是整张表里**唯一一个读起来不需要你做任何决定的格子**，而它背后恰恰藏着一个
必须被选的决定。不作为不是中立的——它有一个具体后果（注释还在、不变量没了），
而那个后果**今天没有任何东西会提醒下一个人**。

（象棋那边有个镜像的病：docstring 写着「更正以新事实追加」，而 `game_id` 是主键，
**schema 兑现不了这句承诺**。两家都是文档与执行对不上，方向相反。）

2. **若选 (c)：晚到的那个真结果，在重算序列里按「对局结束时刻」还是「到达时刻」入列？**

   **⚠️ 这一项的风险在四家不是一个形状，别按一家的数外推：**

   | | 顺序规则的影响 |
   |---|---|
   | **国象** | **低**：中位 0.301 分，最大 1.128（实测 75 组）。用户基本看不见。 |
   | **围棋** | **高，而且是量子化的**：平时差 0，**跨阈值时差一整档段位**。见下。 |
   | 象棋 | 可能**零风险**（delta 已冻结，若只是加法则与顺序无关）——**未验** |
   | 五子棋 | 未验 |

   围棋的具体例子（净胜分 = 2 时，A 是被顶掉那局的真结果=胜，B 是新下的一局=负）：

   | 顺序 | 结果 |
   |---|---|
   | 先 A：`net 2→3` ⇒ **升一档**、归零；再 B：`net −1` | **rung+1**, net=−1 |
   | 先 B：`net 1`；再 A：`net 2` | **rung+0**, net=2 |

   ⇒ **围棋这一项不是脚注，是真决定**：绝大多数时候两种规则毫无差别，
   但一旦净胜分正好卡在阈值上，差的是**一级段位**。
3. **若选 (c)：那笔暂记的负已经占了一个对账序号。更正时这个号留着，还是再消耗一个？**
   （仅五子棋有此序号；他们倾向**留着**——「同一局的裁决被修正」和「又结算了一次」
   应该长得不一样。）

## 🔴 另有一条，比上面三个选项更该先看

### 这次简化会**激活**几处今天够不着的缺陷

**释放占位的每一条路径，都必须在账本里留下痕迹。** 两家已实测，形态不同、后果一样：

| | 实测 |
|---|---|
| 国象 | 无墓碑 + 删预约 ⇒ 晚到的真结算 **404** ⇒ 盒端归永久失败 ⇒ 真实结果被丢弃（有阳性对照：有墓碑则 200 拿回执） |
| 象棋 | 作废预约时连**终端凭证**一起删 ⇒ 晚到的真结算 **401** ⇒ 盒端当成要重新登录 ⇒ outbox 阻塞、结果丢弃，**且云端没有任何记录证明这一局存在过** |

**关键是象棋把可达性分清了**——这一条我认为比缺陷本身更重要：

> **今天不可达**：作废只有**下棋的那台盒子自己**在开局失败/取消路径上调用，
> 它不会去作废一局自己刚下完的棋。
> **新模型下变可达**：释放占位的发起方变成**另一台设备**，
> 而那台设备恰恰不知道这一局有没有被下完。

⇒ **它今天之所以没出事，靠的是「只有当事人能按那个按钮」。而这次简化恰好废掉了这个前提。**

**这类「靠可达性活着的正确性」，四家里很可能不止这一处。** 我认为这是本次简化最大的
系统性风险——不是我们要改的那部分写错了，而是**改动把一批原本够不着的老缺陷送进了射程**。
它不在任何一份「要删什么」的清单里，因为那些代码我们一行都没碰。

### 能不能先于上面的决定落地？**部分能，我原来说得太满**

我先前判断这条「不依赖 (a)/(b)/(c)」。**五子棋指出在他们那儿不成立**：他们有**两条**释放路径
（夺占位 / 清扫器还空占位），墓碑要求不一样——第二条的墓碑要不要、记什么，**恰恰取决于
(a)/(b)/(c) 选了哪个**。

⇒ 修正的排法：**「必须留痕」这条原则可以先统一；每条路径的墓碑记什么，等决定。**
落地前四家先各自数清**自己有几条释放路径**。
