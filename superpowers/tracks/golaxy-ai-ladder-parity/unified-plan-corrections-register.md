#### 2-1 🔴 锁序：总体规划里**一个字都没有**，而现在有两条相反的实测

### ✅ 象棋已接受，并提议院规——**等五子棋/国象会签**

象棋实测的**完整**顺序比原表更具体：**两边都先拿 `users`**，所以**环不在 `users` 上，

| | 顺序 |
|---|---|

### ⚠️ 但象棋的原措辞会误判五子棋自己 —— 五子棋修正，此处采纳

象棋原句是「同一事务内**一律** `users → reservation → ledger → profile`」。
**五子棋实测：它的 settle 根本不显式锁 `users`。**
`settlement_service.py` **既不 import 也不调用 `lock_user`**：

```
lock_reservation(:105) → ledger_for_game(:112) → lock_profile(:148)
```

它对 `users` 那一行的锁，是**插 `RankedLedger`（`:251`）时外键隐式取的 `FOR KEY SHARE`**；
只有 `reserve_game(:83)` 显式 `lock_user`。

⇒ 照原句写进正本，**五子棋那条已有真 PG 交错测试守着的 settle 路径会被判成不合规**，
而**下一个照规矩去「修」它的人，会给一条已验证的路径加一把它并不需要的锁。**

#### ✅ 会签版本（五子棋提出，围棋采纳；这才是让现有代码成立的那条）

> **1.** 显式取 `users` 行锁时，它必须是**最外层**，且必须 `FOR NO KEY UPDATE`。
> **2.** `users` 之下顺序固定 `reservation → ledger → profile`，**跨栈不得反序**。
> **3.** 只通过外键**隐式**取到 `users`（插子表时的 `FOR KEY SHARE`）的路径，
>    **不需要**显式先锁 `users`——因为 `FOR NO KEY UPDATE` 不阻塞 `FOR KEY SHARE`，
>    **这正是 `762e1b39` 拆环的原理**。
> **4.** 新增会插带 `users` 外键的行的写路径，注释里点明它隐式取 `FOR KEY SHARE`，
>    并确认此前没持 `users` 的 `FOR UPDATE`。

**第 3 条是关键**：没有它，规则与现有代码打架；有了它，**规则解释了现有代码为什么是对的**。

> 通则价值：**一条会把现存正确实现判成违规的"统一规范"，比没有规范更危险**——
> 它会驱动别人去改一条本来是对的路径。定规范前先拿现有实现回归验一遍。

#### 2-2 🔴 跨盒接管的 `terminal_kind` 在契约里没有位置，照抄象棋会**复制一个账本缺陷**

- **目标**：§4 强制终局　**来源**：五子棋 track，源码核实
- **实测**：终局契约只有 `board` / `resign` / `system_fault` 三类，而 `resign` **硬性要求**
  `resigned_color == reservation.player_color` **＋原设备认证＋单局 credential**——
  **跨盒接管这三样一样都没有**（发起的是另一台盒子）。象棋记成普通 `resign`，
  于是账本上「本人认输」与「失联被接管」**长得一模一样**，审计/申诉/幂等/对账全失真。
- 🔴 **并行影响：强串行点。** 只要总体规划还写着「接管抄象棋」，后面每一家都会复制这个缺陷。
  **必须先补契约**（谁造 canonical bytes、幂等命令 ID 从哪来、第二种认证模式怎么防混淆、
  重试时 hash 怎么保持一致），**再让任何一家开工接管**。
