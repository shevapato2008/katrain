# S4 大厅 · 裁定（2026-08-26）

## 裁定

**(a)，而且比 (a) 更硬：不是「今天不往里投」，是「盒子上这一屏永远等不到第二个人」——
S4 收缩成「把屏 01 那张『在线大厅』卡在盒子构建里撤下 + 登记理由」，功能一律不做；
三条不鉴权端点 **S1 已经全部收口并配了红绿对照的回归测试**，不需要 S4 再动。**

判别位不是「有没有人用过」，是**结构上能不能有第二个人**。答案是不能，而且有三道各自独立的锁。

---

## 理由

### 1. 盒子上的大厅是一个**进程内的内存字典**，装不下第二台盒子

`LobbyManager` 的在线名单就是一个 `Dict[int, Set[WebSocket]]`，活在 uvicorn 进程里
（`katrain/web/session.py:334-339`）。`/users/online`（`katrain/web/api/v1/endpoints/users.py:58-64`）、
`/games/active/multiplayer`（`katrain/web/api/v1/endpoints/games.py:24-26`）、
`/ws/lobby`（`katrain/web/server.py:2369`）**三个入口全读同一个进程的 `app.state`**，
一处都不过 `RepositoryDispatcher`、不过 `remote_client`。
⇒ 「在线」的定义是「连着**这一个** uvicorn 进程」，不是「连着云端」。

板模式的 lifespan 自己把这句话写在注释里了：

```python
# katrain/web/server.py:444
# Lobby/matchmaker placeholders (not used in board mode but needed by endpoints)
app.state.lobby_manager = LobbyManager()
```

### 2. 三道独立的锁，任何一道都足以把盒子上的大厅锁成「一个人」

| # | 锁 | 出处 |
|---|---|---|
| ① | 盒子上的 katrain **只监听 127.0.0.1** —— 同一个局域网里别的设备连不上，谈不上"另一个人登进来" | `smartbox-software/provisioning/systemd/smartbox-katrain.service:21`（`--host 127.0.0.1`），`:14` 同时设 `KATRAIN_MODE=board` |
| ② | 前端拼 WS/HTTP 地址用的是 `window.location.host` —— 盒子浏览器打的是 127.0.0.1，请求**必然**落回本机，不可能打到云端大厅 | `katrain/web/ui/src/utils/websocketUrl.ts`（`window.location.host`）；`LobbyPage.tsx:143-146` 两条 fetch 都是相对路径 |
| ③ | 严格 box SSO 只保留**一个** `active_generation`，换身份时把已有 socket 全关掉 ⇒ 同一时刻盒上只有一个活身份 | `katrain/web/core/box_sso.py:38-40`、`:62-64` |

再加一条独立佐证：板模式的 `user_repo` 是**本机 SQLite**、登录建的是 shadow user
（`katrain/web/server.py:373`、`katrain/web/api/v1/endpoints/auth.py:181`），
所以「在线名单」的候选池本身就只有在这台盒子上登录过的账号。

⇒ **盒子上打开屏 06，屏上永远是「在线 1 人 · 这是你」「现在没有人在下」。**
这不是空态，是**这一屏在这个部署形态下的唯一态**。

### 3. `lobby_ui.py:14` 那条排除，理由查证过、今天仍然成立 —— 但它管的不是这件事

原文（`smartbox-software/lobby-platform/api/lobby_api/lobby_ui.py:14`）：
「围棋不在内：它不接共享后端（D1），大厅屏由 katrain 自己托管」。
D1 的理由在 `docs/superpowers/specs/2026-08-18-multichess-lobby-design.md:35-60` 被从推断升级成查证：
围棋人人对局的终局数子**必经 KataGo**（`server.py:_complete_count` 那句
"Please wait for KataGo analysis to complete."；`game.py:330 manual_score()` 第一件事就是读
`ownership`，同样是 KataGo 的输出）⇒ 属于「缺了就不能下棋」的必需依赖，
不能塞进共享 lobby 进程（同一条理由也排除了五子棋的 renju/swap2，见同文件 `:834`）。

**这个理由没过期。但它只说了「围棋不进那个共享平台」，没说「围棋的大厅只能活在盒子本机」。**
两者是不同的话 —— 象棋/五子棋/国象的大厅是**云端**的共享进程（跨盒可见），
围棋的大厅是**每台盒子各自一份**的内存字典（跨盒不可见）。
⇒ 差距不在「邀请表不完整」，在于**围棋根本没有一个跨设备的大厅进程**。
这就是为什么 (b) 那 2–4 天买不到任何盒上可见的能力：它修的是岛上的路灯。

### 4. 同一份代码在**云端**是真的有人用的 —— 所以 S1 那三条修补不是白做

galaxy 的 `HvHLobbyPage` 读的是**一模一样的三个入口**
（`katrain/web/ui/src/galaxy/pages/HvHLobbyPage.tsx:61`、`:77`、`:103`、`:171`、`:177`）。
云端 katrain 是 server 模式、多用户同进程 ⇒ 那里的大厅是**真的**。
⇒ 「反正没人用」对盒子成立、对云端不成立；S1 的三条收口是必要的，而且已经做完（见下节）。
⇒ 反过来说：**decline / 段位列 / 完整邀请表的受益人全在云端 galaxy 那一侧，不在这条 kiosk track 上。**

### 5. 盒子上真正的联网对弈走的是别的路，大厅确实是孤岛

- **人人、同一块盘**：本地对局已发货（`/kiosk/play/pvp/setup`，`PlayPage.tsx:118-123`）——
  盒子是共享设备（家里/教室），两个人面对面下棋走的是这条，不需要大厅。
- **人人、跨设备**：走**跨平台**那一族。OGS adapter 是真的能力齐全的：
  `supports_live_play=True` / `supports_automatch=True` / `supports_seek_graph=True`
  （`katrain/web/platforms/ogs/adapter.py:70/72/74`），而且它**不是** `comingSoon`
  （`katrain/web/ui/src/kiosk/constants/platforms.ts` 里只有 fox 是）。
- **人机、跨设备**：星阵（`supports_engine_play` → `/kiosk/play/cross-platform/engine/golaxy`）。

⇒ 盒子上「和别的人下棋」这件事，屏 01 上已经有两条走得通的入口，
第三张卡（在线大厅）是唯一一条**按下去必然什么都遇不到**的。

## 不鉴权端点怎么收口

**先纠正派单里的一处过期前提：这三条 S1 已经全部改完并合进分支了，不是留给 S4 的。**
我逐条读过实现和测试：

| 端点 | 当时的缺陷 | 现状 | 守它的测试 |
|---|---|---|---|
| `GET /api/v1/games/active/multiplayer` | 完全不鉴权，裸吐所有在跑的 `session_id` | 已挂 `current_user: User = Depends(get_current_user)`（`endpoints/games.py:14`），注释写明了为什么 | `tests/web_ui/test_lobby_boundaries.py:92` —— 匿名 401 **加一条带凭据 200 的正对照**（否则 401 可能只是路不通） |
| `GET /api/v1/users/online` | `response_model=User`，把 `uuid`/`credits`/`is_admin`/`net_wins` 发给任何登录用户 | 换成 `OnlineUser`（`katrain/web/models.py:189-205`），**收窄放在响应模型上而不是端点里手挑字段** —— 手挑的写法在 `User` 以后加字段时会静默漏出去 | `test_lobby_boundaries.py:108` —— 逐条断言四个字段不在，外加「别收窄过头」的正对照 |
| `ws /ws/lobby` 的 `accept_invite` | 拿客户端给的任意 `target_id` 直接建局并把 `match_found` 推给对方 ⇒ 任何登录用户能把任意在线用户拽进一局棋 | 判别位换成「他到底邀请过我没有」：`lobby_manager.consume_invite()`（`server.py:2502`、`session.py:381-385`），一次性、TTL 120s、下线作废 | `test_lobby_boundaries.py:152`（没邀请 → 不建局）、`:172`（真邀请 → 建局，正对照）、`:192`（同一封邀请开不出第二局） |

**残余面，逐条给处置：**

1. **`/games/active/multiplayer` 仍是全局名单** —— 任何登录用户看得见每一局的 `session_id`
   和双方用户名。**保持现状，不再收窄**：那正是大厅左栏这个产品功能本身，
   而利用链的两半都封住了（`guard_session_reader`，`server.py:709` + 9 个调用点；
   判负那一半上游的 `guard_session_terminator`）。收窄它等于把云端大厅的左栏废掉。
2. **`OnlineUser` 里的 `rank`/`elo_points` 是 DB 列默认值，不是真值**
   （`models_db.py:75` 的 `default="20k"` 从注册那天起没人写过）。
   这不是安全问题，是**诚实性**问题，而且它今天正在云端说假话：
   galaxy 的 `HvHLobbyPage.tsx:245` 拿 `rank==='20k' && !elo` 判「No Rank」
   ⇒ **定过级的人在云端大厅里被标成「无段位」**。
   kiosk 屏 06 当初拒绝画这一列，理由就是这个（`LobbyPage.tsx:44-52`）—— 判断是对的。
   ⇒ 处置：**登记为 galaxy 侧的缺陷**，修法是 `/users/online` join
   `ai_ladder_profiles.ai_ladder_rung` → `ai_ladder_catalog` 的 `rank_name`（`:23`），
   一处改两屏都对。**不在 kiosk track 里顺手做**（转判据不转结论：这条 track 的判据是盒子）。
3. **`invite` 没有限流** —— 云端任何登录用户能对任意在线用户刷弹窗。
   盒子上不存在（没有第二个人）。登记，不做。
4. **`decline_invite` 缺席**：屏上那句话今天说的是实话
   （`LobbyPage.tsx:511`「拒绝只关掉这个窗 —— 对面收不到回音」），所以**没有谎要修**。
   galaxy 那颗（`HvHLobbyPage.tsx:327` 直接 `setInvitation(null)`）是**同样的空操作但没说出来** ——
   同上，登记为 galaxy 侧。

> 「盒子上撤了卡，这几个端点是不是就没人管了」—— 不是。它们在云端 server 模式下是活的、
> 有真用户（galaxy），所以上面那三条测试必须留着、必须继续跑。
> **撤的是盒子上那张卡，不是这条代码路径。**
