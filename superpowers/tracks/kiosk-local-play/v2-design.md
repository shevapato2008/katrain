## 3. 对局屏与结束流程（S2、S3）

### 3.1 右栏（仅 `game_type === 'pvp_local'`）

- 按键：「领地 · AI 支招 · 数子 · 停一手 · 认输」→ **「数子 · 停一手 · 认输」**。
- 「坐标 / 手数」两个显示开关保留。
- 「数子要下满 N 手」的 N 读状态里的 `count_min_moves`（§3.4），前端不再写死 100。
- 后台分析不关：`GamePage` 里 `wantAnalysis` 仍为真，每换一手调一次 `analyzeCurrent`，数子读的就是这份分数。**不能顺手关掉**，关了数子必定 400。
- 自由对弈、升降级的右栏不变。

### 3.2 两个出口

| 键 | 行为 |
|---|---|
| 左上「退出对局」 | 未终局：确认框「这局还没下完，退出后不会保存」，两个键「继续下 / 退出不保存」→ `DELETE /api/session/{id}` + `clearActiveSession('game')` → 回对弈首页。已终局：直接离开 |
| 右栏红键「认输」 | 确认框「谁认输？」，三个键「黑方认输 / 白方认输 / 取消」→ `POST /api/resign {session_id, color}` → 终局卡 |

**后端契约 · 认输：**

- `/api/resign` 接受可选 `color: "B" | "W"`，用单独的请求模型，不往共享的 `ToggleAnalysisRequest` 里加字段。
- `game_type == "pvp_local"`：必须带 `color`，`end_state = f"{对方}+R"`。不带返回 400。
- 其它模式：带了 `color` 返回 400（免得被静默忽略）；不带则行为不变（仍是 `current_node.player + "+R"`）。

### 3.3 玩家卡上的钟（仅本地对局，S3）

| 状态 | 大字 | 副标 |
|---|---|---|
| 设了用时 · 主时间阶段 | 剩余主时间 `09:42` | `读秒 30秒×3` |
| 设了用时 · 读秒阶段 | 本次读秒剩余 `00:24` | `读秒 · 剩 2 次` |
| 用尽（后端判负前的一瞬） | `00:00` | `超时` |
| 不限时 | 不变（`第 N 手` / `不限时`） | — |

- 轮到谁，谁的钟走。
- 倒计时算法从共享的 `components/PlayerCard.tsx:111-140` 抽成一个纯函数，放在共享区 `src/utils/`。`PlayerCard` 和 kiosk `GameControlPanel` 都用它，免得两份算法走散。**这是共享区改动，两个构建都要跑。**

**判负流程：**

1. 前端算出轮到的一方「主时间 = 0 且读秒次数用尽」时，调 `POST /api/timeout`。只在本地对局、并且设了用时的时候调。
2. 后端在 `pvp_local` 会话上，先 `update_timer()`，再判是否已用尽。判据：`timer 未暂停 ∧ 主时间剩余 ≤ 0 ∧ next_player.periods_used ≥ byo_periods`。`byo_length` / `byo_periods` 取和 `update_timer` 同一套 `max(1, …)` 之后的值，前端倒计时的纯函数也用这一套。
   - 已用尽：`end_state = f"{对方}+T"` → 落账 → 返回 state。
   - 未用尽：**409**，body 附带最新 state。前端用它重算，钟重新走到 0 才再调一次。
3. 终局卡显示「黑方超时负」。
4. 非 `pvp_local` 会话：`/api/timeout` 行为不变。

### 3.4 双 pass 与数子（S2）

**后端：**

- 新增状态位 `awaiting_count`。同时满足下面五条时为真：
  1. 盒上模式，即会话的 `suppress_auto_eval` 为真（galaxy 走不到）；
  2. `game_type ∈ {"free", "pvp_local"}`；
  3. 当前节点和父节点都是 pass；
  4. `current_node.end_state` 为空，也就是没被认输、超时、数子写过真结果；
  5. `manual_score` 为空。
- `awaiting_count` 为真时：
  - `play_move` 的双 pass 落账钩子**不落账**（`server.py:995-1002`）；
  - `/api/count/request` **跳过手数门槛和「已终局」检查**。
- `get_state` 下发 `awaiting_count` 和缩放后的 `count_min_moves = round(base × n² / 361)`，其中 `base` 读 `game/count_min_moves`，默认 100。
- `/api/count/request` 的门槛检查用同一个缩放公式。**这一条全局生效，galaxy 的 9/13 路也受益。**
- `/api/count/request` 补上归属校验，和 `/api/resign`、`/api/timeout` 用同一道 `guard_session_terminator`（P18）。
- 分析还没回来时返回 400，`detail` 带一个**机器可读的原因码**，比如 `analysis_pending`，和其它 400（门槛不够、已终局）区分开，前端才能说出真实原因（P6）。

**前端：**

- 看到 `awaiting_count === true`，自动调数子，显示「正在数子…」。
- 遇到 `analysis_pending`：退避重试，总时长大约 15 秒。超时后说真实原因——「还在算这一手的形势」，或者网络层失败时说「分析服务连不上」——并给「重试」键。
- 手动点「数子」失败时也按原因码出文案，不再一律说「手数不足或已结束」。
- 适用本地对局和自由对弈。

**需要计划阶段核实的一点：** 自由对弈里 AI 自己 pass 结束的局，今天走不到 `play_move` 的钩子（AI 的着手来自 genmove 线程），可能**从来没落过账**。`awaiting_count` 由前端驱动数子，这条路会被顺带补上。计划要先核实，并加一条测试。

### 3.5 落子方式判定（S1，屏 04 + 屏 02）

- **开局那一刻**算出这一局下不下实体盘：`设备能用 ∧ 偏好开着 ∧ 路数 == 19`。结果随活动会话记下（`activeSession`）。
- `PlayInputGuard` 和 `GamePage` **读同一个值**，不再各自判断（P8）。
- 偏好本身（`writePlayOnBoard`）语义不变：它仍是「我倾向下在盘上」，不会因为选了 9 路就被改写。

### 3.6 LED（S0 验，D5）

代码不改。基线走查专测三件事：让子放置灯、提子拿除灯、`removal_pending` 期间对局会不会僵住。僵住就按缺陷单列修复。
