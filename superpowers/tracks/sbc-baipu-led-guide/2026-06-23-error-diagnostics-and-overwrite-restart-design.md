# 2026-06-23 标定诊断卡片与同目录覆盖重启设计

## 状态

已实施并完成自动化验证。

## 背景

真机摆谱过程中出现两类产品问题：

1. 自动标定失败时前端直接展示 `anchor_not_found:15,15` 这类内部错误码，操作者无法判断原因和下一步动作。
2. 摆谱页面点击“重新开始”后只清理前端进度，后端仍根据旧 `manifest.json` 对同一手数返回幂等结果，导致旧的 `frame_000.jpg`、`frame_001.jpg` 等不会被重新拍摄。

## 决策

- 标定错误提示采用 mockup B：诊断卡片。
- “重新开始”采用同一 SGF 目录内覆盖旧帧，不创建新 run 目录。

## 设计

### 标定诊断卡片

前端把后端错误码翻译为面向操作者的诊断信息：

- `anchor_not_found:<row>,<col>` 显示为“无法定位 `<GTP 坐标>` 的定位灯”，例如 `anchor_not_found:15,15` 对应 `Q4`。
- `board_moved` 显示为“摄像头或棋盘位置发生变化”。
- `non_empty_baseline` 或包含 `empty baseline` 的错误显示为“棋盘没有清空，无法建立空盘基线”。
- 其它错误显示通用“自动标定失败”，但保留一行弱化的技术细节，便于开发排查。

当状态为 `failed` 且 `last_valid=true`、摄像头在线时，页面允许操作者点击“网格无误，使用上次标定”。这覆盖服务重启后棋盘未移动、但用户误点“开始自动标定”导致失败的场景。`degraded` 仍禁止复用，因为漂移监测已经判断网格失效。

### 同目录覆盖重启

摆谱重启时前端进入显式覆盖模式：

- 点击 resume 对话框里的“重新开始”后，清空本地进度、重置帧计数和最近保存文件名，并把本次会话标记为 `overwrite_existing=true`。
- 初始帧和后续确认落子都把 `overwrite_existing` 传给 `/api/v1/baipu/capture`。
- 后端收到 `overwrite_existing=true` 且命中已有 `applied_move_index` 时，不返回幂等旧帧，而是重拍并覆盖同名文件。
- 为避免旧尾帧污染训练集，覆盖命中点之后的 manifest 条目会被裁掉，并删除对应旧 `frame_*.jpg`。后续摆谱继续复用 `frame_001.jpg`、`frame_002.jpg` 的顺序文件名。

### 保持不变

- 非重启场景仍保留幂等保护：重复确认同一手且图片存在时返回原记录，不重拍。
- 如果操作者手动删除了某一张坏图，现有缺帧修复逻辑仍原地重拍该槽位，不裁剪后续 manifest。
- 训练集当前阶段仍完全信任操作者，不做棋子识别和摆错判定。

## 验收

1. `failed + last_valid + anchor_not_found:15,15` 前端展示诊断卡片，标题包含 `Q4`，并提供“网格无误，使用上次标定”按钮。
2. `degraded + last_valid` 不显示复用按钮。
3. 重启后首个 `/baipu/capture` 请求包含 `overwrite_existing:true`，且不会在 resume 对话框未选择前抢拍初始帧。
4. 后端 `overwrite_existing=true` 会覆盖旧 `frame_000.jpg` 并裁掉旧尾帧；默认重复请求仍幂等。
