# 评审反馈 (Adversarial Review)

这是一份针对「SBC Pure Play Remote Analysis」需求与实现计划的对抗式评审报告。

## 发现清单

### [Blocker] ref_id 包含 nonce 导致防连点/防重复扣费失效
* **位置**: plan.md - 阶段 4 · 付费分析 handler 
* **问题**: 计划中 `ref_id` 的生成规则为 `f"{session}:{node_id}:{kind}:{nonce}"`。如果前端在用户每次点击时生成一个新的 `nonce`，用户疯狂连点同一个节点的同一个分析功能，后端会认为这是多个不同的 `ref_id`，从而绕过数据库的 `UNIQUE` 约束，导致对同一节点的同一分析**多次扣费**。这是极大的逻辑漏洞，会导致用户被多扣分，且完全无法防并发连点。
* **建议**: 移除 `nonce`，将 `ref_id` 定义为 `f"{session}:{node_id}:{kind}"`。同一局、同一节点、同一种分析只允许成功扣费一次。如果业务上确实需要失败重试，应当由后端判定：检查账本中是否已有该 `ref_id` 且未退款，有则直接返回历史结果或拒绝；只有当发现对应记录是“已退款”时，才允许重新扣费（或前端直接换一个类似 `...:retry1` 的 ref_id，但前端不能无脑每次带随机 nonce）。更简单的防线是前端拿到成功结果后置灰不可点。

### [Blocker] "先扣分-再分析-失败退款" 架构导致宕机吞积分
* **位置**: plan.md - 阶段 4 · 付费分析 handler
* **问题**: `spend -> 跑一次分析 -> 失败 grant 退款` 是在内存中按序编排的非事务过程。由于分析阶段调用远程引擎耗时可能长达数秒，如果在此期间后端进程 Crash、重启或外部网络彻底挂掉，用户的积分已经被扣除入库，但“退款”回调永远不会执行。这将造成“吞积分”的严重不一致。
* **建议**: 对于单体小应用，最轻量的解法是用 `try...finally` 严防应用层面的 Exception 漏接，并在 DB 中记录一条 pending 状态；更彻底的做法是采用“冻结 (pending) -> 分析 -> 成功则核销 (commit) / 失败则解冻 (rollback)”模型；如果为了赶工期不改架构，**必须在计划中明确指出该风险**，并给出应对（如管理员手工后台补单）的兜底方案。

### [High] 兑换码接口缺乏防爆破 / 频控机制
* **位置**: plan.md - 阶段 2 · API `POST /billing/redeem`
* **问题**: 无论是 Kiosk 设备还是 Web 用户，都可以写脚本疯狂并发请求 `/billing/redeem` 来爆破 6 位或 8 位兑换码。计划中没有提及任何针对单 IP 或单用户的 Rate Limit / 防爆破机制。
* **建议**: 必须增加限流机制（例如：同一个用户/IP，每分钟最多尝试 5 次错误，超过则返回 429 或封禁一段时间）。

### [High] Admin 鉴权机制处于“薛定谔”状态，可能引发越权
* **位置**: plan.md - 阶段 2 · API `POST /billing/admin/*`
* **问题**: `requirements.md` 和现有代码事实指出，当前系统没有对 Admin 角色的定义。计划里只写了“校验 admin”，但在落地阶段 2 的数据模型变更时却**遗漏**了对 `User` 表增加角色或 `is_admin` 权限字段的计划。如果没有字段支撑，代码实现时鉴权将无从谈起或被迫硬编码。
* **建议**: 在阶段 2 的数据模型修改中，必须显式说明在 `User` 表增加 `is_admin = Column(Boolean, default=False)` 字段，并在 `auth.py` 中增加对应的 JWT Role / Admin 验证拦截器。

### [Medium] 付费分析的 KataGo Priority 设置不明
* **位置**: plan.md - 阶段 4 · 付费分析 handler
* **问题**: 计划中明确了抑制 `PRIORITY_DEFAULT (1002)` 的自动 eval，但是对于**用户主动触发的付费分析**（领地/支招等）该用什么 priority 并未交代。如果用得太低，会被其它后台任务阻塞；如果比 genmove 还高，可能会阻塞 AI 落子。
* **建议**: 明确指出付费分析所使用的查询 priority。对于主动消费动作，其优先级应该较高（例如紧贴 genmove 或设定为 `PRIORITY_HIGH`），以保证付费用户的即时体验。

### [Medium] UI 改造状态解耦风险 (对弈 vs 复盘)
* **位置**: plan.md - 阶段 5 · 前端:移除对弈页 `ScoreGraph`
* **问题**: 计划要求在对弈页移除胜率图表，而在复盘报告中保留。在 React/Kiosk 单页应用中，对弈和复盘往往共享大量组件。如何准确判定并控制？单纯依靠显隐切换容易引入 Bug。
* **建议**: 明确前端依靠什么状态（如检查 `game_state.is_over` 结合模式，或者专门的 `is_review_mode` 属性）来精准控制 `ScoreGraph` 和付费分析按钮的互斥展示。

### [Low] 真支付 Webhook 验签防重放没有留坑
* **位置**: plan.md - 阶段 6 · API `/billing/webhook/{provider}`
* **问题**: 计划提到该接口现阶段为空壳。但真正接入微信/支付宝时，Webhook 验签必须获取原始的 Request Body（不可解析为 JSON）和 Headers。如果在 FastAPI 框架层面现在写死了普通 JSON body 接收，日后接真网关时必然要重构路由。
* **建议**: 路由设计说明中显式标注：该接口必须预留接收 `Request` 对象并提取 raw body 和 headers 的能力，以备后续验签防重放使用。

## 总体评估与总结

### Top 3 必改
1. **重构 `ref_id` 防重扣策略**：必须移除 `nonce`（或将其作为有限重试标记由后端验证），坚决堵住狂点导致的多扣漏洞。
2. **填补 Admin 权限与防爆破**：增加 `User.is_admin` 字段和管理接口限流，防止越权与兑换码被恶意刷取。
3. **正视“扣费-退款”宕机缝隙**：对分析超时/中断提供更强健的 try-except-finally 兜底退款，并在无法处理断电宕机时提供管理员手动补偿方案。

### 可砍 / 过度设计
* `RechargeOrder` 的 `expired` 等状态对于本期纯 `ManualConfirm` 的半人工场景来说有些过度设计。人工打款截图审核很难产生秒级的“过期”，可以暂不实现定时清理过期订单的 Cron，节省开发成本。

### 一句话总体判断
**计划整体非常清晰、架构解耦到位且分步可落地，但“防重扣费（ref_id nonce 设计）”、“恶意爆破”以及“宕机吞积分”等边界状态存在直接危害资产安全的漏洞；补齐防线后即可放心开工。最大单点风险在于 `ref_id` 滥用机制造成的错误扣分客诉。**
